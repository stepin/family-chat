Статус: черновик от 2026-11-14. Написан после решения владельца: WebDAV на роутере настроить не удалось, для дома это должно быть просто, поэтому сервером становится собственная программа на Rust с хранением в файловой системе и сроком хранения не больше 90 дней.

## 1. Цель и принципы

Семья из 2-20 человек переписывается через программу, запущенную дома. Установка: скачать один файл, запустить, открыть адрес в браузере.

1. **Один исполняемый файл, одна папка с данными.** Без базы данных, без Docker как обязательного условия, без отдельного веб-сервера. Клиент встроен в сервер.
2. **Сервер видит только шифртекст.** Сообщения, вложения, названия групп и состав ключей шифруются на клиенте, как в PLAN.md. Сервер знает, кто в каком чате и когда писал: без этого он не может доставлять.
3. **Сервер задаёт порядок и срок.** Номер сообщения и время ставит сервер, он же удаляет всё старше срока хранения.
4. **Клиент остаётся архивом.** Сервер хранит не больше 90 дней. Всё более старое есть только на устройствах; перенос на новое устройство идёт файлом архива.
5. **Честность про ограничения.** Интерфейс прямо говорит, кому приходится доверять (раздел 3).

## 3. Модель угроз

Защищаем:

- **Переписку от других участников.** Сервер не отдаёт пользователю чужие чаты, а отданное зашифровано ключами, которых у него нет.
- **Переписку на диске.** Тот, кто получил папку данных (резервная копия, украденный накопитель, любопытный взгляд в файлы), видит только шифртекст и то, кто с кем и когда переписывался.
- **Подлинность.** Сообщение от имени Алисы может создать только владелец ключа Алисы.

Не защищаем:

- **От того, кто управляет сервером, если клиент встроен в сервер.** Сервер отдаёт JavaScript клиента, значит его администратор может подменить клиент и украсть ключи. Для семьи это обычно один из родителей. Кому этого мало, открывает клиент с адреса проекта (раздел 5), тогда администратор сервера видит только шифртекст. *(Отменено в M8: клиента с адреса проекта нет, приложение открывается только со своего сервера; см. `docs/SECURITY-MODEL.md`.)*
- Доступность: администратор может удалить данные, сервер может быть выключен.
- Метаданные от администратора сервера: кто, кому, когда, размер. От остальных участников они теперь скрыты.
- Forward secrecy: ключи чатов статичны в пределах эпохи. Компрометация устройства раскрывает то, что лежит на сервере (не больше 90 дней), и локальный архив.
- Push-сервисы Apple, Google и Mozilla узнают время уведомлений и адрес сервера; содержимого и имён они не видят.

## 4. Артефакты и структура монорепозитория

```
family-chat/
  server/            # Rust: программа fcd (HTTP API, хранение, очистка, push, встроенный клиент)
  packages/
    protocol/        # TypeScript: идентичность, шифрование, форматы событий. Без ввода-вывода
    core/            # TypeScript: клиент API (Transport), синхронизация, локальная база, поиск. Без DOM
  apps/
    web/             # веб-клиент (PWA); при сборке сервера встраивается в fcd
    site/            # статичный сайт: что это, как установить, скачать
  docs/
    PROTOCOL.md      # спецификация: API сервера и форматы шифрования, с тестовыми векторами
```

Артефактов три: сервер, веб-клиент, сайт. Исходное требование "два артефакта" расширено: сервер появился вместо роутера.

Из сделанного в первом M0 остаются каркас монорепозитория, CI и страница проверки устройства. Реализация `Storage` для WebDAV, зонд WebDAV, рецепты прокси и `tools/dav-dev` больше не нужны; удаляются при начале M1.

Стек сервера: Rust (стабильный), `tokio`, `axum`, `serde`, `ed25519-dalek` (проверка подписей), `rust-embed` (клиент внутри файла), `web-push` или своя реализация RFC 8291 на `p256` и `aes-gcm`, `clap`, `tracing`. Версии фиксируются при начале M1. Шифрование переписки сервер не выполняет вовсе: в нём нет ключей чатов.

Стек клиента прежний: TypeScript, pnpm, Vite, Svelte 5, Vitest, Playwright. Лицензия MIT.

## 5. Установка и развёртывание

```bash
fcd --data /path/to/family-chat-data
```

При первом запуске сервер создаёт папку данных и печатает адрес и одноразовый код администратора. Администратор открывает адрес, вводит код, создаёт профиль и выпускает приглашения.

Настройки (флаги или `config.toml` в папке данных): порт (по умолчанию 8787), имя семьи, срок хранения в днях (от 7 до 90, по умолчанию 90), предел размера файла (по умолчанию 200 МБ), включён ли push.

HTTPS. Сервер слушает обычный HTTP в домашней сети; HTTPS даёт одно из трёх:

1. Роутер или домашний обратный прокси завершает HTTPS и пересылает на порт сервера (KeenDNS с доменом на устройство и порт, Caddy, прокси в NAS, Cloudflare Tunnel). Основной путь.
2. Свои файлы сертификата: `--tls-cert`, `--tls-key`.
3. Встроенный ACME (Let's Encrypt) при своём домене и пробросе порта 443. Не входит в M1.

Какой из путей сработает у владельца, покажет M0v2. Как именно настраивается KeenDNS для стороннего устройства, взято из общего знания о продукте и не проверено.

Клиент и адреса:

- По умолчанию клиент открывается с адреса сервера. CORS не нужен, отдельного хостинга нет.
- Клиент, открытый с одного сервера, может подключить второй сервер (требование "несколько серверов"). Для этого сервер отвечает с `Access-Control-Allow-Origin: *`: вход идёт по токену в заголовке, cookie не используются, поэтому открытый CORS не даёт чужой странице ничего без токена.
- Тот же клиент публикуется на адресе проекта. Кто не хочет доверять администратору сервера, пользуется им.

Обновление: заменить файл `fcd` и перезапустить. Клиент встроен, поэтому клиент и сервер всегда одной версии. Формат папки данных имеет номер версии; сервер отказывается запускаться на папке более новой версии.

Сборки: Linux x86_64, aarch64, armv7 (статические, musl), macOS, Windows, образ Docker. Сборка под `mipsel` по возможности (предпосылка S3).

## 6. Хранение на диске

```
<data>/
  config.toml                  # настройки
  server.json                  # serverId, имя, версия формата, идентификаторы администраторов
  vapid.json                   # ключи Web Push, права 0600
  users/<userId>/
    identity.json              # подписанный конверт: открытые ключи
    profile.json               # подписанный конверт: имя, аватар, ревизия
    avatar.<sha8>.<webp|jpg>
    devices/<devId>.json       # хэш токена, даты, подписка push
    keys/<n>.key               # запечатанные ключи групп для этого пользователя
    removed                    # отметка: пользователь исключён
  invites/<хэш кода>.json      # одноразовые приглашения со сроком
  chats/<chatId>/
    meta.json                  # вид (dm или group), участники для доставки, владелец, эпоха, версия состояния
    state/<version>.enc        # зашифрованное и подписанное состояние группы
  log/<YYYY-MM-DD>.seg         # все события дня, только дозапись
  log/<YYYY-MM-DD>.del         # номера стёртых событий этого дня
  blobs/<YYYY-MM-DD>/<blobId>/<NNNN>   # части вложений по 4 МиБ
  tmp/                         # незавершённые записи
```

- **Журнал.** Один файл на день (UTC, часы сервера). Запись: `длина u32 | gseq u64 | время u64 мс | chatId | senderId | devId | эпоха u32 | тело | crc32`. Тело это зашифрованное событие, сервер его не разбирает. `gseq` это сквозной номер события на сервере, растёт на единицу.
- **Запуск.** Сервер читает файлы журнала и строит в памяти индекс (номер, чат, файл, смещение). При 20 людях и сотнях сообщений в день это десятки тысяч записей за 90 дней. Оборванная последняя запись (нет полной длины или не сходится crc32) отбрасывается.
- **Надёжность записи.** Событие дозаписывается в файл дня и сбрасывается на диск (`fsync`) до ответа клиенту. Файлы состояния, профиля, приглашений пишутся во временный файл и переименовываются.
- **Один писатель.** Запись в журнал идёт через одну задачу внутри сервера. Папку данных держит один процесс (файл-блокировка).
- **Очистка.** Раз в час сервер удаляет `log/<день>.seg`, `log/<день>.del` и `blobs/<день>/` старше срока хранения. Точка отсчёта: меньшее из "сейчас" и "время самого свежего события плюс 7 дней". Так часы, прыгнувшие в будущее, не стирают всё; часы, сброшенные в прошлое, просто откладывают очистку.
- **Что не чистится.** `users/`, `chats/<chatId>/meta.json` и `state/`, ключи групп: они маленькие, и без них восстановленное устройство не прочтёт текущую эпоху. Чат без событий в пределах срока остаётся в списке пустым.
- **Резервная копия.** Копия папки данных при остановленном сервере. Времена файлов значения не имеют.
- **Место.** Текст за 90 дней при предельной нагрузке занимает десятки мегабайт [estimated]; место определяется вложениями. Сервер показывает занятое и свободное место администратору и отвечает 507, когда свободного меньше порога.

## 7. Протокол

### 7.1. Что остаётся от PLAN.md

- Идентичность: seed, фраза из 24 слов, `userId` из открытого ключа подписи, `identity.json` и `profile.json` как подписанные конверты.
- Ключ личного чата: `dmKey = HKDF(X25519(мой секрет, boxPub собеседника), "fc/v1/dm" || serverId || sort(idA, idB))`.
- Группы: один владелец, эпохи, ключ эпохи запечатывается каждому участнику по HPKE (RFC 9180), состояние подписано владельцем и несёт цепочку владения от создателя.
- Событие: подпись автора и AES-256-GCM ключом эпохи, дополнение до кратного 256 байт. В AAD и в подпись вместо имени файла входят `serverId`, `chatId`, эпоха и `id` сообщения.
- Вложения: части по 4 МиБ, свой ключ на файл, nonce равен номеру части.
- Виды событий (`msg`, `edit`, `delete`, `react`, `leave`), поля `dev` и `seq` для обнаружения потерь, версии полезной нагрузки с отметкой `crit`.
- Архив `.fcarchive` для переноса истории.

### 7.2. Что исчезает

Метки чатов по дням, почасовые корзины, таблица `seen`, закрытие корзин, сверка листингов, правила часов клиента, очистка клиентами, поле `sv` и правила развилок состояния, отсечка по `seq` для удалённых авторов, пакеты дней, фоновая дозагрузка лет истории, планировщик запросов с приоритетами, зонд WebDAV.

Причина одна: сервер упорядочивает события и проверяет, кто участник.

### 7.3. Вход и устройства

- Приглашение: одноразовый код (128 случайных бит), срок 7 дней, выпускает администратор. Ссылка `https://<сервер>/#invite=<код>`; фрагмент убирается из адресной строки после чтения. Пароля в ссылке нет, использованный код не действует.
- Вступление: клиент создаёт идентичность и отправляет код, `identity.json`, профиль и идентификатор устройства. Сервер проверяет подписи и выдаёт токен устройства (256 случайных бит). На диске хранится только хэш токена.
- Второе устройство и восстановление по фразе: клиент просит у сервера случайное число, подписывает его ключом идентичности и получает токен нового устройства. Приглашение не нужно.
- Исключение: администратор удаляет пользователя. Его токены перестают действовать сразу, сервер больше не принимает от него событий и не отдаёт ему новые. Владельцы групп получают служебное событие и меняют эпоху, чтобы исключённый не прочёл новое и из старой копии ключа.
- Первый вошедший по коду администратора становится администратором. Назначить второго можно командой `fcd admin add <userId>`.
- Ограничение частоты: неверный код или подпись с одного адреса не чаще 10 раз в минуту.

### 7.4. Чаты, состояние и эпохи

- Личный чат создаётся первым сообщением: сервер сам заводит `meta.json` с двумя участниками.
- Группа создаётся одним запросом: состояние версии 1, список участников для доставки, запечатанные ключи каждому. Сервер пишет всё или ничего.
- Смена состояния (название, участники, владелец, новая эпоха): один запрос с условием "текущая версия равна N". Сервер принимает его только от владельца и только если версия совпала. Двух версий одного номера быть не может, поэтому развилок нет.
- Список участников в `meta.json` нужен серверу для доставки. Конфиденциальность от него не зависит: сервер, добавивший лишнего читателя, отдаст ему шифртекст без ключа. Клиенты сверяют список сервера с подписанным состоянием и показывают расхождение.
- Эпоха записана в открытом заголовке события. Событие со старой эпохой сервер отклоняет ответом 409; клиент получает новый ключ, шифрует заново и отправляет. Сообщение при смене эпохи не теряется и не дублируется.
- Выход: событие `leave`; сервер сразу убирает участника из доставки, владелец меняет эпоху при следующем запуске.

### 7.5. API

Все запросы под `/v1`, вход: `Authorization: Bearer <токен>`. Тела JSON, кроме событий и частей вложений (байты).

| Запрос | Назначение |
|---|---|
| `GET /hello` | без входа: версия протокола, `serverId`, имя семьи, срок хранения, предел файла, открытый ключ push, время сервера |
| `POST /join` | вступление по приглашению, ответ: токен |
| `POST /auth/challenge`, `POST /auth/device` | новое устройство по подписи ключом идентичности |
| `GET /users` | участники семьи: идентичности и профили |
| `PUT /me/profile`, `PUT /me/avatar` | свой профиль |
| `GET /chats` | мои чаты: вид, участники, версия состояния, эпоха |
| `POST /chats` | создать группу |
| `PUT /chats/<id>/state` | сменить состояние, условие по версии |
| `GET /chats/<id>/state/<version>` | прочитать состояние |
| `GET /keys?after=<n>` | мои запечатанные ключи групп |
| `POST /chats/<id>/events` | отправить событие; заголовок `Idempotency-Key` равен `id` сообщения; ответ: `gseq` и время |
| `GET /events?after=<gseq>&limit=500&wait=25` | мои события после номера; если новых нет, ждёт до 25 секунд |
| `GET /chats/<id>/events?before=<gseq>&limit=200` | история чата назад, для прокрутки |
| `DELETE /chats/<id>/events/<gseq>` | "удалить у всех": автор или владелец группы |
| `PUT /blobs/<blobId>/<part>`, `GET /blobs/<blobId>/<part>`, `DELETE /blobs/<blobId>` | вложения |
| `PUT /me/push`, `DELETE /me/push` | подписка на уведомления для этого устройства |
| `POST /admin/invites`, `GET /admin/invites`, `DELETE /admin/invites/<id>` | приглашения |
| `GET /admin/users`, `DELETE /admin/users/<id>` | участники и исключение |
| `GET /admin/stats` | место на диске, число событий, версия |

Правила:

- Повтор отправки с тем же `Idempotency-Key` возвращает прежний `gseq` и не создаёт второго события.
- "Удалить у всех" затирает тело записи нулями в файле дня и добавляет номер в `.del`; вложения сообщения удаляются. Остальным клиентам приходит служебное событие об удалении.
- Сервер проверяет: участие в чате, размер события до 256 КБ, размер части, предел файла, формат идентификаторов (только ожидаемая длина и алфавит).
- Ошибки: 401 (токен недействителен; клиент пробует войти заново подписью), 403 (исключён или не участник), 409 (версия состояния или эпоха устарела), 410 (запрошенное уже удалено по сроку), 413, 429, 507.
- Вложение доступно любому вошедшему пользователю, знающему `blobId` (128 случайных бит из сообщения). Удалить его может загрузивший.

### 7.6. Синхронизация

- У клиента один курсор на сервер: последний полученный `gseq`. Пока приложение открыто, клиент держит запрос `GET /events?...&wait=25` и сразу повторяет его.
- Новое устройство получает всё, что лежит на сервере (не больше 90 дней), страницами по 500 от новых к старым чатам; чаты доступны после первой страницы.
- Если курсор старше самого раннего события на сервере, клиент показывает в чатах отметку "сообщения до <дата> с сервера уже удалены" и предлагает импорт архива с другого устройства.
- Потери: `seq` в полезной нагрузке растёт на единицу для пары (устройство, чат); пропуск виден в диагностике.
- Отправка: событие в локальную очередь, затем `POST`; при обрыве повтор с тем же `Idempotency-Key`. Очередь разбирает один исполнитель (Web Locks).
- Время и порядок в ленте берутся из ответа сервера. Часы телефона ни на что не влияют.

### 7.7. Уведомления

- Сервер при первом запуске создаёт ключи VAPID. Клиент после разрешения пользователя подписывается и отдаёт подписку серверу.
- На новое событие сервер шлёт уведомление устройствам участников чата, кроме устройства отправителя и чатов "без звука". Полезная нагрузка: идентификатор чата и `gseq`, зашифрованные для браузера по RFC 8291. Service worker показывает "Новое сообщение" и имя чата из локальной базы; текст показывается, только если пользователь включил это и service worker смог расшифровать событие.
- Подписка, которую push-сервис объявил недействительной, удаляется.
- Администратор может выключить push целиком (`push = false`): тогда сервер не обращается ни к каким внешним адресам.
- На iOS уведомления приходят только установленному на экран "Домой" приложению.

## 8. Экраны: что меняется

Раздел 8 PLAN.md остаётся основой (23 экрана, три маршрута входа, состояния, доступность). Поправки:

## 10. Тесты

- Сервер, модульные: кодек записи журнала; восстановление после обрыва на любом байте последней записи (property-тест); очистка при часах, прыгнувших вперёд и назад; условная смена состояния; повтор с тем же `Idempotency-Key`; одноразовость приглашения; отзыв токенов при исключении.
- Сервер, интеграционные: процесс `fcd` на временной папке, сценарии через HTTP: вступление, два пользователя, длинный запрос, чужой чат недоступен (403), предел размеров, перезапуск посреди отправки, вторая копия сервера на той же папке не запускается.
- Протокол: тестовые векторы шифрования и подписей в `docs/`, независимая проверка скриптом, отрицательные векторы (перенос события в другой чат и на другой сервер, подложенное состояние, неверный AAD).
- Сквозные (Playwright против настоящего `fcd`): два и три клиента, группа, удаление участника и смена эпохи с сообщением, отправленным в этот момент, восстановление по фразе, исключение из семьи, экспорт и импорт архива.
- Уведомления: модульный тест шифрования полезной нагрузки на векторах RFC 8291; ручная проверка на iOS и Android.
- Бюджеты [estimated]: запуск сервера с журналом за 90 дней (18 тыс. событий) быстрее 2 секунд на устройстве уровня Raspberry Pi 3; новое устройство получает 90 дней быстрее 1 минуты в домашней сети; память сервера меньше 50 МБ.
- Остаются из PLAN.md: доступность, маршрут приглашённого на iPhone, устойчивость разбора, набор XSS-строк, проверка нарушений CSP, миграции локальной базы, поиск по 100 тыс. сообщений.

## 11. Вне рамок v1

Звонки и видео, индикатор набора, отметки о прочтении, превью ссылок, forward secrecy, встроенный ACME, сборка под MIPS как обязательная, несколько администраторов через интерфейс, федерация серверов, синхронизация архива между своими устройствами через сервер, хранение дольше 90 дней.

## 12. Решения, принятые по умолчанию

План исходит из этих значений. Каждое можно изменить одной фразой, и ни одно не блокирует начало M1:

1. **Срок хранения.** Всё на сервере, включая текст, не больше 90 дней. Это отменяет решение UC3 первого гейта. Цена: потерянный телефон без файла архива теряет переписку старше 90 дней.
2. **Шифрование остаётся сквозным.** Сервер на Rust мог бы хранить открытый текст, и это было бы проще. Оставлено, потому что исходное требование было "участники не подсматривают чаты друг друга", а папка данных и её копии не должны читаться.
3. **Клиент встроен в сервер.** Один адрес, никакого CORS и хостинга. Цена описана в разделе 3: администратор сервера технически может подменить клиент.
4. **Уведомления через Web Push включены.** Это отменяет решение UC1 "асинхронная переписка": оно принималось, когда уведомления требовали отдельного ретранслятора. Сервер обращается к push-сервисам Apple, Google и Mozilla; выключается одной настройкой.
5. **Доставка длинным запросом**, без WebSocket: он проходит через любой прокси и работает в service worker.
