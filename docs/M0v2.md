# M0v2: сервер `fcd` дома, HTTPS и уведомления

> Это инструкция для первой проверки на этапе M0v2, она сохранена как история. Установка и настройка сервера
> сейчас описаны в [ADMIN.md](ADMIN.md), вопросы и решения в [FAQ.md](FAQ.md). Страница `/server/` и флаг `--m0`
> работают по-прежнему.

Этап M0v2 (`docs/PLAN-v2.md`, раздел 9) отвечает на три вопроса:

1. Где будет работать сервер и доступен ли он с телефонов дома и из мобильной сети.
2. Проходит ли длинный запрос на 25 секунд через выбранный способ HTTPS.
3. Доходит ли уведомление Web Push до установленного приложения на iPhone и Android.

Чата пока нет. Есть сервер `fcd` и страница проверки `/server/`, встроенная в него.

## 1. Сборка

Нужны Node 22+, pnpm 11 и Rust (stable). Клиент встраивается в исполняемый файл, поэтому сначала собирается он:

```bash
# в корне репозитория
pnpm install
pnpm build                                   # собирает apps/web/dist
cargo build --release --manifest-path server/Cargo.toml
# готовый файл: server/target/release/fcd (около 3,5 МБ)
```

Если забыть `pnpm build`, `cargo build` остановится с сообщением, что нет `apps/web/dist/index.html`.

### Сборка под Linux (роутер, NAS, Raspberry Pi, мини-ПК)

Статические файлы под musl, без зависимостей от системы. Удобнее всего собирать в Docker, тогда на своей машине не
нужен ни компилятор под чужой процессор, ни rustup. Команды запускаются из корня репозитория после `pnpm build`.

aarch64 (Raspberry Pi 3/4/5 с 64-битной системой, многие NAS и роутеры на ARM64):

```bash
docker run --rm -v "$PWD":/src -w /src/server \
  -e CARGO_TARGET_DIR=/src/server/target/docker-aarch64 rust:1-alpine sh -c \
  'apk add --no-cache musl-dev && cargo build --release --locked --target aarch64-unknown-linux-musl'
# результат: server/target/docker-aarch64/aarch64-unknown-linux-musl/release/fcd
```

x86_64 (мини-ПК, NAS на Intel/AMD, VPS):

```bash
docker run --rm --platform linux/amd64 -v "$PWD":/src -w /src/server \
  -e CARGO_TARGET_DIR=/src/server/target/docker-x86_64 rust:1-alpine sh -c \
  'apk add --no-cache musl-dev && cargo build --release --locked --target x86_64-unknown-linux-musl'
# результат: server/target/docker-x86_64/x86_64-unknown-linux-musl/release/fcd
```

Что проверено: см. раздел 7 в конце. Образ `rust:1-alpine` собирает под тот процессор, на котором работает Docker;
на Mac с Apple Silicon вариант x86_64 идёт через эмуляцию и собирается заметно дольше.

Без Docker можно через rustup и [cargo-zigbuild](https://github.com/rust-cross/cargo-zigbuild)
(`rustup target add aarch64-unknown-linux-musl`, `cargo zigbuild --release --target aarch64-unknown-linux-musl`).
Этот путь не проверялся.

Роутеры на MIPS (`mipsel`) в Rust поддерживаются на третьем уровне, и сборка может потребовать ночной компилятор
(предпосылка S3). В M0v2 эта сборка не готовилась.

## 2. Запуск

```bash
./fcd --data /path/to/family-chat-data --m0
```

- `--data` это папка данных. При первом запуске сервер создаёт её и печатает в журнал адрес и **код администратора**
  (`XXXX-XXXX-XXXX-XXXX`). Код показывается один раз; сохраните его. Если код потерян: остановите сервер и выполните
  `fcd reset-admin-code --data <папка>`.
- `--m0` включает проверочные точки этого этапа (длинный запрос и пробное уведомление). Они работают только с кодом
  администратора. Без флага их нет.
- Остановка: Ctrl+C или `kill <pid>` (SIGTERM). Второй экземпляр на той же папке не запустится и скажет об этом.

Настройки задаются флагами или в `config.toml` в папке данных (файл создаётся при первом запуске; флаги важнее):

| Флаг | В `config.toml` | По умолчанию |
|---|---|---|
| `--port` | `port` | 8787 |
| `--listen` | `listen` | `0.0.0.0` (все адреса) |
| `--family-name` | `family_name` | Семья |
| `--retention-days` | `retention_days` | 90 (от 7 до 90) |
| `--max-file-mb` | `max_file_mb` | 200 |
| `--push true\|false` | `push` | `true` |
| | `push_subject` | `mailto:fcd-admin@example.org`: контакт, который сервер передаёт push-сервисам Apple, Google и Mozilla. Значение по умолчанию ничьё; если уведомления на iPhone не приходят, задайте здесь свой адрес (`mailto:` или `https://`) |

Подробнее о журнале: переменная `RUST_LOG` (например, `RUST_LOG=debug`).

Сразу после запуска откройте на ноутбуке в той же сети `http://<адрес устройства>:8787/server/`. Страница должна
показать «Сервер отвечает». Это проверка без HTTPS; телефонам для уведомлений нужен HTTPS.

## 3. HTTPS: три способа

Сервер слушает обычный HTTP. HTTPS с настоящим сертификатом нужен браузеру для service worker, уведомлений и
установки приложения. Попробуйте способ, который вам ближе; в отчёте напишите, какой сработал.

### Способ 1. Роутер или обратный прокси перед сервером (основной путь)

Что-то в домашней сети принимает HTTPS на своём адресе и пересылает запросы на `http://<устройство>:8787`.

- **KeenDNS на роутере Keenetic.** Идея: домен KeenDNS для устройства в домашней сети с пересылкой на порт 8787.
  **Это не проверено.** Как именно это настраивается и пропускает ли облачный режим KeenDNS долгие запросы, мы не
  знаем; пошаговой инструкции здесь нет, чтобы не выдумывать. Пробуйте по документации Keenetic и обязательно
  проверьте длинный запрос: облачный режим может обрывать соединения.
- **Caddy** на любом компьютере в сети, если есть свой домен и проброс портов 80 и 443 на этот компьютер. Caddy
  сам получает сертификат Let's Encrypt. Минимальный `Caddyfile`:

  ```
  chat.example.com {
      reverse_proxy 192.168.1.10:8787
  }
  ```

- **Встроенный прокси NAS** (Synology, QNAP и другие), если NAS умеет обратный прокси с сертификатом: то же самое,
  назначение `http://<устройство>:8787`.
- **Cloudflare Tunnel.** Не нужны проброс портов и белый адрес. Для быстрой пробы без учётной записи:
  `cloudflared tunnel --url http://localhost:8787` на машине с сервером печатает временный адрес
  `https://….trycloudflare.com`. Для постоянной работы нужен именованный туннель и свой домен в Cloudflare. Учтите:
  HTTPS завершается у Cloudflare, и Cloudflare видит запросы (переписка в будущем всё равно шифруется на клиенте).

### Способ 2. Свои файлы сертификата

Флаги `--tls-cert` и `--tls-key` (появились в M2): `fcd --data <папка> --tls-cert fullchain.pem --tls-key privkey.pem`.
Подробно в [ADMIN.md](ADMIN.md#свои-файлы-сертификата).

### Способ 3. Встроенный Let's Encrypt

Не входит ни в M0v2, ни в M1.

## 4. Что проверить

Везде открывайте `https://<ваш адрес>/server/`, вводите код администратора и нажимайте кнопки по порядку. Журнал
проверок сохраняется на устройстве, так что отчёт можно скопировать в конце.

### Ноутбук

1. Страница показывает «Сервер отвечает», имя семьи и «Проверки M0: включены».
2. «Проверить длинный запрос (25 с)»: должно быть «Длинный запрос прошёл за 25.x с». Если пришла ошибка раньше, это
   важно: значит, прокси или туннель обрывает долгие запросы.
3. По желанию: «Включить уведомления» и «Прислать пробное сейчас» в Chrome или Firefox.

### Android (Chrome)

1. Дома по Wi-Fi: открыть страницу, «Проверить длинный запрос».
2. Установить приложение: меню Chrome, «Установить приложение» (или «Добавить на главный экран»).
3. Открыть установленное приложение, перейти на «Проверка сервера» (`/server/`), ввести код.
4. «Включить уведомления», разрешить. «Прислать пробное сейчас»: уведомление должно появиться.
5. «Прислать через 1 минуту», сразу закрыть приложение (смахнуть из списка недавних). Через минуту должно прийти
   уведомление. Нажать на него: откроется приложение, в журнале появится «приложение открыто нажатием на
   уведомление».
6. Выключить Wi-Fi и повторить шаги 1 и 5 через мобильную сеть.

### iPhone (iOS 16.4 или новее, Safari)

На iPhone уведомления работают только у приложения, добавленного на экран «Домой». В Safari страница так и скажет.

1. Дома по Wi-Fi в Safari: открыть страницу, «Проверить длинный запрос».
2. «Поделиться», затем «На экран "Домой"». Открыть приложение с экрана «Домой».
3. В приложении открыть «Проверка сервера», ввести код (у приложения своё хранилище, код и журнал из Safari туда не
   переходят).
4. «Включить уведомления», разрешить. «Прислать пробное сейчас».
5. «Прислать через 1 минуту», закрыть приложение (смахнуть вверх из переключателя приложений). Дождаться уведомления,
   нажать на него.
6. Выключить Wi-Fi и повторить шаги 1 и 5 через мобильную сеть.

Если уведомление не пришло: посмотрите журнал сервера. Для каждого пробного уведомления там есть строка
`test push sent` с адресом push-сервиса и ответом (201 значит принято) или `test push failed` с причиной.

## 5. Что прислать обратно

1. Отчёт со страницы (кнопка «Скопировать отчёт») с каждого устройства: ноутбук, iPhone, Android. Кода администратора
   в отчёте нет. В нём есть адрес сервера и `serverId`: не выкладывайте отчёт публично.
2. На чём работает сервер: устройство, процессор (`uname -m`), система, какая сборка `fcd` запустилась.
3. Каким способом получен HTTPS (KeenDNS, Caddy, NAS, Cloudflare Tunnel, другое) и что пришлось настроить.
4. Прошёл ли длинный запрос дома и в мобильной сети.
5. Дошли ли уведомления на iPhone и на Android: при открытом приложении и при закрытом, дома и в мобильной сети.
6. Строки журнала сервера с `test push`, если уведомления не дошли. Код администратора из первых строк журнала не
   присылайте.

## 6. Что сервер хранит сейчас

```
<data>/
  config.toml     настройки
  server.json     serverId, версия формата папки, хэш кода администратора (права 0600)
  vapid.json      ключи Web Push (права 0600); не публикуйте этот файл
  fcd.lock        блокировка: папку держит один процесс
  users/ invites/ chats/ log/ blobs/ tmp/   пока пустые, понадобятся с M1
```

Сервер на папке с более новой версией формата не запустится. Удалить `vapid.json` значит сменить ключи: подписки на
уведомления на всех устройствах перестанут работать до повторного «Включить уведомления».

## 7. Что проверено при подготовке

- Сборка и тесты на macOS (Apple Silicon): `cargo test`, `cargo clippy`, сквозной тест Playwright в Chromium против
  настоящего `fcd`.
- Шифрование уведомлений сверено с тестовым вектором RFC 8291; формат запроса к push-сервису (заголовки, подпись VAPID,
  расшифровка тела) проверен против поддельного push-сервиса в тестах.
- **Доставка через настоящие push-сервисы Apple, Google и Mozilla не проверялась**: браузеры в Playwright не умеют
  подписываться на них. Это и есть главная ручная проверка этапа.
- Сборка под Linux aarch64 (musl) командой из раздела 1 на Mac с Apple Silicon: собирается, файл статический
  (около 3,6 МБ), запускается в контейнере `busybox:musl`, отвечает на `/v1/hello`, корректно завершается по SIGTERM.
  На настоящем роутере, NAS или Raspberry Pi не запускался.
- Сборка под Linux x86_64 (musl) командой из раздела 1 там же, через эмуляцию amd64 в Docker: собирается (около 7 минут
  с нуля), файл static-pie около 4,2 МБ, `fcd --version` в контейнере `busybox:musl` работает. Сервер из этой сборки
  не запускался дальше `--version`.
