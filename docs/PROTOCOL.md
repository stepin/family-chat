# Family Chat: протокол v1 (идентичность, личные чаты, группы, события, вложения, архив, стикеры)

> **Криптография этого протокола не проходила независимого аудита. И не планируется.** Конструкции собраны из стандартных примитивов (Ed25519, X25519, HKDF-SHA-256, AES-256-GCM, BIP39), но их сочетание никто со стороны не проверял.

Документ описывает форматы, которые реализует пакет `packages/protocol`, достаточно подробно, чтобы по нему можно было написать совместимую реализацию. Тестовые векторы лежат в `docs/vectors/`, их независимо проверяет скрипт `packages/protocol/scripts/verify-vectors.mjs`, который пользуется только `node:crypto`.

Что входит: идентичность и фраза восстановления, конверты `identity`, `profile`, `auth`, отзыв идентичности (раздел 4.5), ключ личного чата, формат события, полезные нагрузки `msg`, `edit`, `delete`, `react` (раздел 7), группы с собственным происхождением и цепочкой владения (раздел 14), запечатывание секрета эпохи по HPKE (раздел 15), вложения (раздел 16), контейнер архива `.fcarchive` (раздел 17), наборы стикеров (раздел 18). Почему форматы устроены именно так, объясняет раздел 10.

API сервера (запросы, коды ответов) описывается отдельно, в `docs/API.md` (его ведёт автор сервера).

## 1. Обозначения

| Запись | Значение |
| --- | --- |
| `a \|\| b` | склейка байтовых строк |
| `utf8(s)` | байты строки `s` в UTF-8 |
| `u32(n)` | 4 байта, беззнаковое целое, big-endian |
| `lp(x)` | `u32(длина x в байтах) \|\| x`; для строки `x` берётся `utf8(x)` |
| `"…"` в формуле | байты ASCII-строки без завершающего нуля; `\n` это байт `0x0a` |
| `HKDF(ikm, info)` | HKDF-SHA-256 по RFC 5869, **соль пустая** (то есть 32 нулевых байта), длина результата 32 байта |
| `SHA-256(x)[0..n]` | первые `n` байт хэша |
| base64url | RFC 4648, раздел 5, **без** `=` |
| base32 | алфавит RFC 4648 (`a-z2-7`), **строчные буквы**, без `=` |

Правило для всех подписываемых и хэшируемых строк: каждое поле переменной длины (строки, байтовые идентификаторы, полезная нагрузка) идёт через `lp()`. Целые числа идут как `u32`. Метки домена (`"fc/v1/…"`) стоят в начале и префикса длины не имеют: они постоянны и у разных конструкций разные.

Декодеры base64url и base32 строгие: отвергают `=`, символы вне алфавита, заглавные буквы в base32, невозможную длину и ненулевые «хвостовые» биты последнего символа. Так у каждой байтовой строки ровно одна текстовая форма, и сравнение идентификаторов как строк корректно.

## 2. Примитивы

| Задача | Примитив | Реализация в клиенте |
| --- | --- | --- |
| Подпись | Ed25519, RFC 8032 (детерминированная) | `@noble/curves` |
| Обмен ключами | X25519, RFC 7748 | `@noble/curves` |
| Хэш, вывод ключей | SHA-256, HKDF-SHA-256 | `@noble/hashes` |
| Шифрование событий, состояний, частей вложений, блоков архива | AES-256-GCM, nonce 96 бит, тег 128 бит | WebCrypto (`crypto.subtle`) |
| Запечатывание секрета эпохи | HPKE, RFC 9180: base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM | собственная реализация в `src/hpke.ts` на `@noble/curves`, `@noble/hashes` и WebCrypto |
| Фраза восстановления | BIP39, английский словарь | `@scure/bip39` |
| Случайность | `crypto.getRandomValues` | платформа |

Проверка подписи Ed25519 идёт по правилам RFC 8032 без послаблений ZIP-215: неканонические кодировки точки и скаляра отвергаются. Открытый ключ подписи малого порядка отвергается при проверке `identity` (раздел 4.2). Серверу на `ed25519-dalek` следует пользоваться `verify_strict`: он отвергает то же самое и дополнительно слабые ключи, которые до него не дойдут, потому что клиент их не создаёт.

## 3. Идентичность

### 3.1. Seed и фраза восстановления

- **seed**: 32 случайных байта. Из него выводится всё остальное.
- **Фраза**: 24 слова английского словаря BIP39. Это сами 32 байта seed как энтропия BIP39: 256 бит энтропии, затем 8 бит контрольной суммы `SHA-256(seed)[0]`, всего 264 бита, разбитые на 24 индекса по 11 бит (старшие биты первыми). Растяжения PBKDF2 из BIP39 (`mnemonicToSeed`) **нет**: фраза кодирует seed, а не пароль к нему.
- Словарь: `docs/vectors/bip39-english.txt`, SHA-256 файла (2048 строк через `\n`, с `\n` в конце) равен `2f5eed53a4727b4bf8880d8f3f199efc90e58503646d9ff8eff3a2ed3b24dbda`.
- Разбор ввода: нормализация NFKD, нижний регистр, разделитель это любая последовательность пробельных символов (переводы строк при вставке допустимы). Затем по порядку:
  1. число слов не 24 → ошибка `phrase-word-count`;
  2. слова нет в словаре → `phrase-unknown-word` с номерами слов (с единицы), чтобы интерфейс подсветил их;
  3. контрольная сумма не сходится → `phrase-checksum` («слово опечатано или стоит не на месте»).
- В тексте ошибок есть только номера позиций, самих слов нет: сообщения об ошибках могут попасть в журнал.

Проверочные значения: seed из 32 нулей даёт `abandon` ×23 + `art`, seed из 32 байт `0xff` даёт `zoo` ×23 + `vote` (это официальные векторы BIP39 для 256-битной энтропии).

### 3.2. Вывод ключей

```
signSecret = HKDF(seed, "fc/v1/sign")   # секретный ключ Ed25519 в форме seed по RFC 8032
boxSecret  = HKDF(seed, "fc/v1/box")    # секретный ключ X25519 (clamping по RFC 7748 при использовании)
selfKey    = HKDF(seed, "fc/v1/self")   # ключ архива (раздел 17)
signPub    = Ed25519 открытый ключ (32 байта)
boxPub     = X25519 открытый ключ (32 байта)
```

Разные метки дают независимые ключи: раскрытие одного не раскрывает другие, и один и тот же материал никогда не служит и для подписи, и для обмена.

### 3.3. userId

```
userId = base32(SHA-256(signPub)[0..16])      # 26 символов a-z2-7
```

Идентификатор удостоверяет сам себя: чтобы выдать свои ключи за чужой `userId`, нужно найти второй прообраз для 128-битного префикса SHA-256 (около 2^128 операций).

### 3.4. Отпечаток для ручной сверки

```
h = SHA-256("fc/v1/fingerprint\n" || lp(signPub) || lp(boxPub))
для g = 0..5:  n_g = h[5g .. 5g+5] как 40-битное целое big-endian;  группа_g = n_g mod 100000, 5 цифр с ведущими нулями
отпечаток = 6 групп через пробел, например "04219 88310 …"
```

30 цифр, около 99 бит. Отпечаток принадлежит одному человеку: Алиса читает вслух свой, Боб сравнивает с тем, что его приложение показывает для Алисы. Сверка защищает от подмены ключей сервером или администратором при первом знакомстве (сервер не должен иметь возможности незаметно выдать один ключ за другой).

## 4. Подписанные конверты

### 4.1. Общий формат

```json
{"payload":"<base64url>","sig":"<base64url>"}
```

- `payload`: точные байты документа JSON в UTF-8.
- `sig`: 64 байта Ed25519 над `utf8("fc/v1/" + kind + "\n") || payload`, где `kind` один из `identity`, `profile`, `auth`, `revoked`, `group-state`, `group-key`.
- `payload` не больше 8192 байт, у `group-state` не больше 65536 байт (в состоянии список участников с ключами).
- Проверка всегда идёт над **полученными** байтами `payload`. Объект не сериализуется заново, каноническая форма JSON не нужна.
- Конверт содержит ровно два ключа, `payload` и `sig`, оба строки. Лишние ключи отвергаются.
- В `payload` неизвестные поля игнорируются; поле `v` обязано равняться `1`, иначе ошибка `unsupported-version`.
- Байты `payload`: строгий UTF-8, без BOM, корневой элемент объект.
- Вид `event` в конвертах запрещён: эта метка занята подписью событий (раздел 6.5). Метка с видом и `\n` в конце не даёт подписи одного вида сойти за подпись другого.

Ключи внутри `payload` клиент пишет в порядке, указанном ниже; проверяющий порядок не проверяет.

### 4.2. identity

```json
{"v":1,"userId":"…","signPub":"<base64url 32 байта>","boxPub":"<base64url 32 байта>","created":<мс>}
```

Подписан собственным `signPub`. Проверка:

1. форма конверта, `v = 1`;
2. `userId` это base32 ровно 16 байт; `signPub`, `boxPub` ровно по 32 байта; `created` целое ≥ 0;
3. `userId = base32(SHA-256(signPub)[0..16])`, иначе `user-id-mismatch`;
4. `signPub` каноническая точка Ed25519 не малого порядка, иначе `invalid-key`;
5. подпись, иначе `bad-signature`.

Защищает: `boxPub` нельзя подменить, не владея ключом подписи; `userId` нельзя присвоить чужим ключам.

### 4.3. profile

```json
{"v":1,"userId":"…","name":"…","avatar":null,"rev":<целое>,"updated":<мс>}
```

Проверяется против уже проверенной `identity` владельца: `userId` совпадает (`user-id-mismatch`), подпись ключом `signPub` этой identity (`bad-signature`).

- `name`: от 1 до 64 кодовых точек Unicode, не пустое после обрезки пробелов; запрещены управляющие символы C0, DEL, C1 и символы управления направлением текста (U+061C, U+200E, U+200F, U+202A-U+202E, U+2066-U+2069), запрещены непарные суррогаты. При создании имя обрезается по краям.
- `avatar`: `null` или объект ровно с двумя ключами, в этом порядке при записи:

  ```json
  {"sha256":"<base64url 32 байта>","type":"image/jpeg"}
  ```

  `sha256` это SHA-256 файла картинки, загруженного через `PUT /me/avatar`; `type` это `image/jpeg` или `image/webp`. Любая другая форма (другие ключи, лишние ключи, другой тип, хэш не 32 байта) даёт `malformed`. Сервер проверяет ту же форму.
- `gender` (необязательное): `"m"` или `"f"`, грамматический род для текстов о человеке («создал»,
  «создала»). Нет поля: `"m"`; клиенты и серверы, которые о поле не знают, его
  не замечают (неизвестные поля игнорируются, раздел 4.1). Любое другое значение (другая строка,
  `"F"`, `null`, число, пустая строка) даёт `malformed`; сервер проверяет то же правило. При записи поле стоит после
  `avatar`: `{"v":1,"userId":"…","name":"…","avatar":null,"gender":"f","rev":<целое>,"updated":<мс>}`. Приложение
  пишет поле всегда (`"m"` или `"f"`). Профиль подписан, но не зашифрован: сервер видит это поле, как и имя.
  Векторы: `docs/vectors/profile-gender.json`.
- `rev`, `updated`: целые ≥ 0. Клиент игнорирует профиль с `rev` ниже уже виденного.

Защищает: имя меняет только владелец ключа; символы смены направления не дают выдать одно имя за другое.

### 4.4. auth (новое устройство)

```json
{"v":1,"userId":"…","serverId":"…","nonce":"…","devId":"…"}
```

- `nonce`: вызов (challenge) сервера, копируется дословно; `serverId`: идентификатор сервера из `/hello`. Обе строки непустые, не длиннее 256 байт UTF-8, содержимое для протокола непрозрачно.
- `devId`: base32 ровно 10 байт (16 символов).
- Проверка: `userId` совпадает с identity (`user-id-mismatch`), подпись (`bad-signature`), затем `serverId` и `nonce` совпадают с ожидаемыми (`context-mismatch`).

Защищает: подпись нельзя повторить (одноразовый `nonce`) и нельзя унести на другой сервер (`serverId`). Сервер обязан выдавать каждый `nonce` один раз и с коротким сроком.

### 4.5. revoked (отзыв идентичности)

```json
{"v":1,"userId":"…","revokedAt":<мс>}
```

Подписан ключом самой отзываемой идентичности: отозвать ключ может только тот, у кого он есть (украденный телефон, перенос на новую идентичность). Проверка против проверенной `identity` владельца: форма, `v = 1`, `userId` base32 16 байт и `revokedAt` целое ≥ 0 (`malformed`), `userId` совпадает (`user-id-mismatch`), подпись (`bad-signature`). Клиент после проверенного отзыва не принимает от этой идентичности событий, состояний и ключей, начиная с `revokedAt`, и показывает отметку в карточке контакта. Что делать с уже принятыми сообщениями, решает клиент.

## 5. Личный чат

### 5.1. Ключ

```
shared = X25519(boxSecret_мой, boxPub_собеседника)          # всё нули → ошибка invalid-key
lo, hi = два userId, упорядоченные побайтно (lo ≤ hi)
dmKey  = HKDF(shared, "fc/v1/dm" || lp(serverId) || lp(lo) || lp(hi))
encKey = HKDF(dmKey,  "fc/v1/enc")                          # ключ AES-256-GCM событий
epoch  = 0
```

- Обе стороны получают один ключ без обмена сообщениями (X25519 симметричен, пара упорядочена).
- Нулевой общий секрет (собеседник прислал точку малого порядка) отвергается: иначе ключ чата был бы известен всем.
- `serverId` в выводе делает ключи одной пары на разных серверах разными.
- Чат с самим собой («Избранное»): та же формула, собеседник это я сам, `lo = hi = мой userId`.

### 5.2. chatId личного чата

```
chatId = base32(SHA-256(utf8("fc/v1/dm\n" + serverId + "\n" + lo + "\n" + hi))[0..16])   # 26 символов
```

Формула совпадает с той, что вычисляет сервер `fcd` (`ChatId::direct`). Здесь, в отличие от остальных конструкций, нет префиксов длины, а разделитель это `\n`. Запись всё равно однозначна: `lo` и `hi` ровно по 26 символов base32, поэтому последние 54 символа всегда `"\n" + lo + "\n" + hi`, а `serverId` это всё между меткой и ними. Метка `fc/v1/dm\n` совпадает по тексту с меткой HKDF `fc/v1/dm` только префиксом, и используется в другой функции (SHA-256, а не `info` HKDF), поэтому значения не пересекаются.

Почему формула открытая (раздел 10, п. 6): так сервер может сам вычислить идентификатор по двум `userId` и проверить, что первый отправитель действительно один из двух участников. С секретной формулой участник мог бы заранее занять идентификатор чужой пары (свой с Бобом он знает) с неверным составом. Состав личных чатов сервер знает и так, поэтому новых метаданных формула не раскрывает.

## 6. События

### 6.1. Тело события (то, что хранит сервер)

```
смещение  длина  поле
0         3      magic = "FC1" (46 43 31)
3         1      format = 0x01
4         4      epoch, u32
8         8      serverTag = SHA-256("fc/v1/server-tag\n" || lp(serverId))[0..8]
16        8      chatTag   = SHA-256("fc/v1/chat-tag\n"   || lp(chatId))[0..8]
24        16     msgId (сырые байты идентификатора сообщения)
40        12     nonce (случайный)
52        N+16   AES-256-GCM(encKey, nonce, plaintext, AAD): шифртекст N байт и тег 16 байт
```

Первые 40 байт это заголовок. Длина тела равна `68 + N`, где `N` (длина открытого текста) кратно 256.

```
AAD = заголовок(40) || lp(serverId) || lp(chatId)
```

### 6.2. Открытый текст

```
смещение  длина  поле
0         16     senderId (сырые 16 байт userId автора, base32-декодированные)
16        64     sig
80        4      len, u32: длина payload
84        len    payload (JSON в UTF-8, раздел 7)
84+len    …      нули до ближайшего кратного 256
```

Дополнение минимальное: `N = ceil((84 + len) / 256) × 256`. Длинное дополнение и ненулевые байты в нём отвергаются (`malformed`), так у одного открытого текста одна запись. Дополнение скрывает точную длину сообщения от сервера и от того, кто видит папку данных.

### 6.3. Подпись автора

```
sig = Ed25519(signSecret_автора,
        "fc/v1/event\n" || lp(serverId) || lp(chatId) || u32(epoch) || lp(msgId) || lp(senderId) || lp(payload))
```

`msgId` и `senderId` здесь сырые 16 байт. Дополнение в подпись не входит.

### 6.4. Шифрование

- `encKey` берётся из ключа чата эпохи (для личного чата раздел 5.1, для группы раздел 14.2).
- nonce: 96 случайных бит на каждое шифрование, включая повторную отправку. При случайном nonce предел безопасности AES-GCM около 2^32 сообщений на ключ; личный чат семьи до него не дойдёт.
- Предел тела события 262144 байта (256 КиБ, предел сервера). Отсюда наибольший открытый текст 261888 байт и наибольший `payload` 261804 байта. Текст сообщения ограничен отдельно (раздел 7.2).

### 6.5. Разбор и проверки

Получатель знает из контекста `serverId`, `chatId`, эпоху (из заголовка сервера) и `encKey`. Проверки идут строго в этом порядке, каждая со своим кодом ошибки:

| # | Проверка | Ошибка | От чего защищает |
| --- | --- | --- | --- |
| 1 | длина ≤ 262144 | `too-large` | исчерпание памяти |
| 2 | длина ≥ 68 + 256 и `(длина − 68)` кратно 256 | `malformed` | обрезанное или испорченное тело |
| 3 | magic `FC1` | `malformed` | чужие данные |
| 4 | format = 1 | `unsupported-version` | формат будущей версии |
| 5 | epoch в заголовке равна ожидаемой | `wrong-epoch` | событие другой эпохи |
| 6 | serverTag | `wrong-server` | перенос события на другой сервер |
| 7 | chatTag | `wrong-chat` | перенос события в другой чат |
| 8 | AES-GCM расшифровал с AAD | `wrong-key` | чужой ключ, изменённые байты, изменённый заголовок (AAD) |
| 9 | `len` помещается, дополнение минимально и из нулей | `malformed` | неоднозначная запись |
| 10 | автор известен вызывающему как участник чата | `unknown-author` | событие от постороннего |
| 11 | автор совпадает с отправителем, о котором сообщил сервер (если передан) | `sender-mismatch` | несогласованность сервера |
| 12 | подпись автора | `bad-signature` | подделка участником, у которого есть ключ чата |
| 13 | `payload` разбирается (раздел 7), `payload.id` равен `msgId` заголовка | `malformed` | подмена идентификатора |

Почему метки в заголовке. GCM не различает причины отказа: другой ключ, другой чат и другой сервер дают одну и ту же ошибку. Метки `serverTag` и `chatTag` (по 8 байт хэша открытых строк) дают точную диагностику до расшифровки. Сами по себе они ничего не защищают: они входят в AAD, а настоящую привязку дают AAD и подпись, где стоят полные строки `serverId` и `chatId`. Метки не раскрывают ничего нового: `serverId` и `chatId` сервер знает и так.

Что ловит подпись, а не AAD. Ключ личного чата знают оба участника. Участник, состоящий и в чате A, и в чате B с общим ключом, мог бы расшифровать событие и зашифровать его заново в другой контекст. AAD такое не поймает (он пересчитан), а подпись поймает: `serverId`, `chatId`, эпоха и `msgId` подписаны автором. Такой перенос даёт ошибку `bad-signature`, а не `wrong-chat` (отрицательный вектор есть в `negative.json`).

Повтор. Сервер или участник может прислать то же тело второй раз. Подпись при этом верна. Повторы отсекает клиент по паре (`senderId`, `msgId`): сообщение с уже виденной парой не показывается второй раз. Сервер со своей стороны отвечает на повтор `Idempotency-Key` прежним `gseq`.

`lookupAuthor`. Решение, кто вправе писать в чат, принимает вызывающий: для личного чата это ровно два участника, для «Избранного» один. Протокол только проверяет, что подпись принадлежит тому, кого вернул `lookupAuthor`.

## 7. Полезная нагрузка

### 7.1. Общие поля всех видов

| Поле | Тип | Смысл |
| --- | --- | --- |
| `v` | целое ≥ 1 | версия вида, сейчас `1` |
| `t` | непустая строка | вид: `msg`, `edit`, `delete`, `react` |
| `id` | base32 16 байт | идентификатор сообщения; равен `msgId` заголовка и заголовку `Idempotency-Key` |
| `dev` | base32 10 байт | устройство-отправитель |
| `seq` | целое ≥ 0 | номер события для пары (устройство, чат), растёт на 1 начиная с 1; пропуск означает потерю |
| `crit` | логическое, необязательно | `true`: вид нельзя пропустить молча |

Времени сообщения в нагрузке нет: время и порядок задаёт сервер. Неизвестные поля игнорируются.

### 7.2. msg

```json
{"v":1,"t":"msg","id":"…","dev":"…","seq":1,"body":"…","reply":{"author":"<userId>","id":"<msgId>"},
 "fwd":true,"attachments":[<описатель>, …],"location":{"lat":55.75,"lon":37.62,"accuracy":25}}
```

- `body`: Markdown, не более 16384 байт UTF-8, если есть, то непустой.
- `reply`: необязательная ссылка на сообщение парой (автор, `id`): участник не может своим сообщением вытеснить чужое.
- `fwd`: только `true` или отсутствует. Отметка «переслано». Автора оригинала в ней нет: получатель не может проверить подпись чужого события из другого чата, а непроверяемое имя позволило бы приписать текст кому угодно.
- `attachments`: список от 1 до 10 описателей вложений (раздел 16.3). Пустой список запрещён.
- `location`: `lat` число от −90 до 90, `lon` от −180 до 180 (градусы WGS 84), `accuracy` радиус точности в метрах, число от 0 до 10^7. Все три обязательны и конечны.
- Отправитель обязан передать хотя бы одно из: непустой `body`, `attachments`, `location`. Получатель принимает `msg` и без них и показывает пустым.
- `sticker`: ссылка на стикер набора семьи `{"pack":"<packId>","file":"<hash32>","type":"webp"|"tgs","w":512,"h":512}` (раздел 18). У такого сообщения `body` обязателен и это эмодзи стикера (правила эмодзи реакции: 1-16 кодовых точек, до 64 байт, без управляющих и bidi-символов и пробелов по краям), а `attachments` и `location` запрещены. Клиент, который о стикерах не знает, поле пропускает и показывает эмодзи: так выполнено правило о старых клиентах без `crit`.
- Порядок ключей при записи: `v, t, id, dev, seq, body, reply, fwd, attachments, location, sticker`. Отсутствующие поля не пишутся.
- Новые необязательные поля не меняют версию `msg`: клиент, который их не знает, их игнорирует.

### 7.2a. edit, delete, react

```json
{"v":1,"t":"edit","id":"…","dev":"…","seq":2,"target":{"author":"<userId>","id":"<msgId>"},"body":"…"}
{"v":1,"t":"delete","id":"…","dev":"…","seq":3,"target":{…},"targetDev":"<devId>","targetSeq":1}
{"v":1,"t":"react","id":"…","dev":"…","seq":4,"target":{…},"emoji":"👍","on":true}
```

- `target`: пара (автор, `id`) целевого сообщения, оба поля строгого формата.
- `edit.body`: строка не больше 16384 байт, может быть пустой (подпись под вложением можно убрать). Правка действует, только если её автор совпадает с `target.author`; это проверяет клиент.
- `delete.targetDev`, `delete.targetSeq`: `dev` и `seq` удаляемого события, чтобы пропуск в нумерации не считался потерей. Удалять может автор сообщения или владелец группы; это проверяет клиент. Без `targetDev` пропуск нельзя отнести к устройству.
- `react.emoji`: 1-16 кодовых точек, не больше 64 байт UTF-8, без управляющих и bidi-символов и без пробелов по краям. `on`: логическое, `true` ставит реакцию, `false` снимает.
- Порядок ключей при записи указан в примерах.
- `crit` у этих видов не ставится: старый клиент их пропускает.

Разбор в коде: `parsePayload` и `decodePayload` (его вызывает `decodeEvent`) возвращают одинаковый типизированный вид для `msg`, `edit`, `delete`, `react`. `payloadCommon(p)` даёт `id`, `dev`, `seq` любого вида.

Как клиент применяет эти виды (`packages/core/src/apply.ts`). Результат не зависит от порядка получения событий: клиент хранит все проверенные события-правки и пересчитывает целевое сообщение из них.

- Порядок между событиями задаёт `gseq` сервера.
- `edit` действует, только если автор правки равен `target.author`. Действует правка с наибольшим `gseq`. Окна времени для правки нет. Правки удалённого сообщения не действуют. Правка, пришедшая раньше сообщения, хранится и применяется, когда сообщение придёт.
- `delete` действует от автора сообщения или от участника, который был владельцем группы в принятом клиентом состоянии эпохи события удаления. Удаление окончательное: сообщение показывается тихой строкой «Сообщение удалено», его текст, правки, реакции и вложения удаляются с устройства. Удаление, пришедшее раньше сообщения, хранится; пришедшее позже сообщение сразу заменяется строкой. Пропуск `targetSeq` устройства `targetDev` потерей не считается.
- `react`: ключ (сообщение, автор реакции, эмодзи), действует значение `on` с наибольшим `gseq`. Один человек может поставить несколько разных эмодзи, одно эмодзи один раз. Реакции удалённого сообщения пропадают.
- Удаление на сервере (`DELETE /v1/chats/<id>/events/<gseq>`, `docs/API.md` 5.6) подписи не имеет: обнулённая запись и служебная запись `event_deleted` не убирают сообщение, которое у клиента есть; они только ставят строку «удалено» туда, где о сообщении ничего не известно.

### 7.3. Неизвестные виды и версии

Вид считается неизвестным, если пара (`t`, `v`) не реализована (реализованы `msg`, `edit`, `delete`, `react` версии 1).

- неизвестный с `"crit": true` → результат `update-required`: интерфейс показывает «Обновите приложение, чтобы увидеть это сообщение»;
- неизвестный без `crit` → результат `ignore`: событие не показывается.

В обоих случаях `id` обязателен и сверяется с заголовком, а `dev` и `seq`, если они правильной формы, возвращаются для учёта потерь. Вида `leave` нет: выход из группы обрабатывает сервер. Служебных видов для групп нет: состояние и ключи идут отдельными запросами (разделы 14, 15).

## 9. Ошибки

Все ошибки пакета имеют тип `ProtocolError` с полем `code`. Коды: `malformed`, `too-large`, `invalid-argument`, `phrase-word-count`, `phrase-unknown-word`, `phrase-checksum`, `unsupported-version`, `invalid-key`, `bad-signature`, `user-id-mismatch`, `context-mismatch`, `wrong-server`, `wrong-chat`, `wrong-epoch`, `wrong-key`, `unknown-author`, `sender-mismatch`.

Коды групп, ключей эпохи и архива:

| Код | Когда |
| --- | --- |
| `not-owner` | состояние или запечатанный ключ подписан не тем владельцем, которого даёт цепочка; изменение подписано не владельцем предыдущего принятого состояния; построитель вызван не владельцем |
| `bad-chain` | `chatId` не выводится из ключа создателя; цепочка передач владения нарушена |
| `invalid-transition` | состояние не следует за предыдущим: номер версии, `prev`, правила эпохи, смена ключей участника |
| `state-mismatch` | состояние не то, на которое ссылается запечатанный ключ (версия или хэш) |
| `wrong-recipient` | запечатанный ключ адресован другому участнику |
| `wrong-identity` | архив записан другой идентичностью | Секретные ключи, seed, слова фразы и открытый текст в сообщения не попадают.

## 10. Решения

Где было несколько вариантов, выбран самый простой безопасный.

 1. **HKDF с пустой солью**, метка домена целиком в `info`. Seed и общий секрет X25519 и так равномерны или близки к этому, соль ничего не добавляет.
 2. **Метки домена в подписях конвертов оканчиваются на `\n`** (`fc/v1/identity\n`), как задано в контракте с сервером. Та же форма использована для событий (`fc/v1/event\n`) и хэшей (`fc/v1/fingerprint\n`, `fc/v1/server-tag\n`, `fc/v1/chat-tag\n`, `fc/v1/dm\n` для `chatId`). Метки HKDF (`fc/v1/sign`, `fc/v1/box`, `fc/v1/self`, `fc/v1/dm`, `fc/v1/enc`) без `\n`.
 3. **Заголовок события в открытом виде** несёт эпоху, `serverTag`, `chatTag` и `msgId`: так различаются ошибки «другой сервер», «другой чат», «другая эпоха», «другой ключ», а получатель знает `msgId` до расшифровки, не завися от того, передаёт ли его сервер.
 4. **`msgId` в AAD и подписи.** Байт после `FC1` это версия формата `0x01`.
 5. **`senderId` в открытом тексте** хранится сырыми 16 байтами, подпись дополнительно покрывает `senderId`.
 6. **Открытый `chatId` личного чата** (раздел 5.2), а не выведенный из секретного `dmKey`. Сервер может его проверить. Формула взята у сервера как есть, поэтому в ней разделители `\n` вместо префиксов длины; однозначность обоснована в разделе 5.2.
 7. **`id` обязателен во всех видах нагрузки**, не только в `msg`: он же `Idempotency-Key` и сверяется с заголовком.
 8. **Времени в `msg` нет**: время и порядок задаёт сервер.
 9. **Отпечаток на одного человека** (30 цифр по ключам одной identity), а не общий «номер безопасности» пары: проще объяснить и показать в карточке контакта.
10. **Строгость проверки Ed25519**: RFC 8032 без ZIP-215, плюс отказ от ключей малого порядка в `identity`.
11. **Имя профиля** проверяется одинаково при создании и при проверке; управляющие и bidi-символы запрещены: отказ проще и однозначнее, чем молчаливая чистка.
12. **Минимальное нулевое дополнение** обязательно; иное дополнение это `malformed`.
13. **`seq` ≥ 0** при проверке (рекомендуется начинать с 1).
14. **`chatId` группы** считается как `SHA-256("fc/v1/group-id\n" || lp(signPub) || lp(nonce))`: метка домена и префиксы длины по общему правилу раздела 1. Nonce 16 байт.
15. **Кто подписывает версию с передачей владения.** Её подписывает прежний владелец (он же подписывает саму передачу), а поле `owner` уже называет нового. Подписант версии `n` это владелец после всех передач с версией меньше `n`. Так у каждой версии ровно один допустимый подписант, и он же владелец предыдущей версии; сервер принимает запрос от него же.
16. **В состоянии есть поле `by`** (кто подписал). Без него нельзя отличить «подписал не владелец» (`not-owner`) от «испорчены байты» (`bad-signature`).
17. **Аватар**: только два ключа, `sha256` и `type`; лишние ключи отвергаются. Совпадает с проверкой сервера.
18. **Удаление участника без новой эпохи запрещено** при проверке перехода (`invalid-transition`), а не только в построителе: иначе удалённый читал бы новое старым ключом.
19. **Ключи участника в группе не меняются** (`invalid-transition`): новый ключ означает новую идентичность и новый `userId`.
20. **Эпохи группы начинаются с 0**, версии состояния с 1, эпоха растёт ровно на 1 (сервер требует то же).
21. **Состояние шифруется `encKey` эпохи**, тем же ключом, что события. Разделение даёт другой magic (`FCS` против `FC1`) в заголовке, который входит в AAD; отдельный ключ не выводится.
22. **Дополнение состояния до 256 байт**, как у событий: длина названия и списка не видна точно.
23. **Подписант запечатанного ключа** это подписант состояния, на которое ключ ссылается. Ключи пишутся вместе с состоянием, поэтому другой подписант не нужен.
24. **HPKE `aad` пустой**: всё связывание в `info`.
25. **`fwd` это только `true`**, без автора оригинала (раздел 7.2).
26. **`delete` несёт `targetDev`** вместе с `targetSeq`: без него пропуск нельзя отнести к устройству.
27. **Миниатюра только JPEG** (проверяются первые байты `FF D8 FF`): кодируется во всех браузерах, список типов задан одним значением.
28. **Части вложения нумеруются с 0**, `nonce = 8 нулевых байт || u32 номер`. В AAD сырые 16 байт `blobId`, а не текст. Ключ файла используется для AES напрямую, без вывода.
29. **В описателе вложения нет дня загрузки**: путь на сервере строит сервер.
30. **Допустимый ряд `partSize`** состоит из одного значения, 4194304. Новое значение потребует новой версии клиента-получателя.
31. **Заголовок архива входит в AAD каждого блока**, а не только первого: так блок нельзя пересадить в архив с другим заголовком, а правило проще.
32. **Проверочное значение `check` в заголовке архива** даёт ясную ошибку `wrong-identity` до расшифровки. Оно выведено из ключа архива и не раскрывает, чей это архив.
33. **Записи архива** до 16 МиБ; большие данные (файлы) клиент режет на несколько записей. Тип записи 0 зарезервирован.
34. **Лимит участников 100**, как у сервера.
35. **Порядок правок и реакций по `gseq`** сервера, а не по часам клиента: порядок и время задаёт сервер.
36. **Право владельца группы удалять** проверяется по владельцам принятых состояний эпохи события `delete`: владелец, передавший владение в той же эпохе, тоже считается.
37. **Сервер не доказывает удаление**: обнулённая запись и `event_deleted` без подписи, поэтому локальную копию убирает только подписанное событие `delete`.

## 11. Что оставлено на потом и как формат это допускает

- **Аватар группы, стикеры**: новые поля состояния и `msg`; неизвестные поля игнорируются.
- **Смысл записей архива**: определяет клиентское ядро (раздел 17.3).
- **Новый формат события, состояния, архива**: байт `format` в заголовке; старый клиент ответит `unsupported-version`.

## 12. Для авторов сервера и клиента

- Сервер может и должен проверять конверты `identity` (раздел 4.2), `profile` и `auth` по правилам раздела 4, над полученными байтами `payload`. Подпись: `utf8("fc/v1/" + kind + "\n") || payload`.
- Сервер не разбирает тело события. Если хочется ранней проверки: длина тела `68 + 256k` и не больше 262144, первые 4 байта `46 43 31 01`, байты 4-7 это эпоха из заголовка запроса (у личного чата 0), байты 24-39 это base32-декодированный `Idempotency-Key`. Всё это необязательно: клиент проверяет сам.
- `chatId` личного чата вычисляется по разделу 5.2, той же формулой, что `ChatId::direct` в сервере; векторы в `dm.json` годятся и для тестов сервера. Эпоха идёт в заголовке `X-FC-Epoch`, `msgId` в `Idempotency-Key`.
- `devId` и `msgId` генерирует клиент; сервер проверяет только длину и алфавит.
- Клиент отбрасывает повторы по (`senderId`, `msgId`) и отслеживает пропуски `seq` по (`dev`, чат).
- Клиенту: `lookupAuthor` должен возвращать проверенную `identity` только участников этого чата; ключи и seed хранить вне журналов и отчётов об ошибках.

Группы и вложения:

- **Группа, создание (`POST /chats`)**: `chatId` из `GroupChange.state.chatId`, `state` это base64url от `GroupChange.blob` (зашифрованное состояние, раздел 14.4), `members` это `userId` из `state.members`, `epoch` это `state.epoch` (0), `keys` это `{userId, key}` для каждого элемента `sealedKeys`, где `key` это `serializeEnvelope(envelope)` (JSON конверта `group-key`, около 700 байт; сервер хранит строку непрозрачно). Сервер не может прочитать состояние: версию, эпоху, участников и владельца он берёт из полей запроса. Заголовок блоба (раздел 14.4) в открытом виде несёт эпоху и версию, сервер может сверить их с запросом.
- **Смена состояния (`PUT /chats/<id>/state`)**: `baseVersion = prev.version`, `owner = state.owner` (после передачи это уже новый владелец, хотя запрос шлёт прежний), остальное как при создании. При новой эпохе ключи нужны всем оставшимся участникам, при добавлении с историей только новичкам, при переименовании и передаче владения ключей нет.
- Сервер вправе проверять конверт `group-key` (поля `chatId`, `epoch`, `recipient`, `stateVersion` читаются без расшифровки, подпись по ключу владельца из `identity`), но это необязательно: клиент проверяет сам.
- **Получение ключа (`GET /keys`)**: клиент вызывает `acceptGroupKey(key, blob, me, {serverId, prev?})`, где `blob` получен из `GET /chats/<id>/state/<stateVersion>`. Затем `groupStateActions(prev, state, me)` говорит, что делать: `needKey`, `removed`, `added`, `renamed`, `ownerChanged`. Следующие версии той же эпохи проверяются `openGroupState(blob, {serverId, chatId, keys, prev})`.
- **Сверка участников**: `compareGroupMembers(state, serverMembers)`; `missingOnServer` у владельца означает выход или исключение, владелец вызывает `removeGroupMembers` (новая эпоха).
- **События группы**: тот же `encodeEvent`/`decodeEvent`, `chat = deriveGroupKeys(секрет, эпоха)`; `lookupAuthor` возвращает участников последнего принятого состояния этой эпохи.
- **Порядок записи у владельца**: сохранить `GroupChange` локально (секрет!), затем один запрос на сервер. При 409 `stale_version` перечитать состояние и построить изменение заново.
- **Вложения (`PUT /blobs/<blobId>/<part>`)**: `blobId` это `blob.id` (26 символов base32, совпадает с форматом сервера), номер части с 0, тело части это вывод `encryptBlobPart` (открытый текст + 16 байт). Части кроме последней ровно 4194320 байт. Событие `msg` отправлять после загрузки всех частей.
- **Аватар**: сервер и клиент проверяют одну форму (раздел 4.3).

## 14. Группы

### 14.1. Идентификатор группы

```
nonce  = 16 случайных байт
chatId = base32(SHA-256("fc/v1/group-id\n" || lp(signPub создателя) || lp(nonce))[0..16])   # 26 символов
```

Тот же алфавит и длина, что у `chatId` личного чата. Группа удостоверяет себя сама: состояние несёт `signPub` создателя и `nonce`, любой может пересчитать `chatId`, а подложенное состояние с чужим `chatId` не проходит проверку (`bad-chain`).

### 14.2. Секрет эпохи

```
secret = 32 случайных байта (свой на каждую эпоху)
encKey = HKDF(secret, "fc/v1/enc")          # та же функция, что у личного чата
```

Первая эпоха 0, первая версия состояния 1. События группы имеют формат раздела 6 с `epoch` группы; сервер отвергает событие со старой эпохой (409), клиент получает новый ключ и отправляет событие заново с тем же `id`.

### 14.3. Состояние

Конверт вида `group-state` (раздел 4.1), payload до 65536 байт:

```json
{"v":1,"serverId":"…","chatId":"…","version":3,"epoch":1,"name":"Семья",
 "creator":{"signPub":"<b64url 32>","nonce":"<b64url 16>"},
 "owner":"<userId>","by":"<userId>",
 "transfers":[{"version":2,"to":"<userId>","toSignPub":"<b64url 32>","sig":"<b64url 64>"}],
 "members":[{"userId":"…","signPub":"<b64url 32>","boxPub":"<b64url 32>"}],
 "prev":"<b64url 32>"}
```

- `version` u32 ≥ 1; `epoch` u32; `name` по правилам имени профиля (раздел 4.3).
- `members`: 1-100 записей, строго по возрастанию `userId` (значит, без повторов); у каждого `userId = base32(SHA-256(signPub)[0..16])`, `signPub` допустимая точка Ed25519. Открытые ключи в состоянии нужны, чтобы восстановленное устройство не зависело от чужих `identity`. Клиент сверяет `boxPub` с известной ему `identity` и показывает расхождение.
- `owner` входит в `members`.
- `prev`: `null` ровно у версии 1, иначе `stateHash` предыдущей версии.
- `stateHash = SHA-256(payload)` над точными байтами.
- Порядок ключей при записи как в примере. Неизвестные поля игнорируются.

**Передача владения.** Каждая запись `transfers` подписана владельцем перед ней:

```
sig = Ed25519(прежний владелец,
        "fc/v1/group-transfer\n" || lp(serverId) || lp(chatId) || u32(version) || lp(signPub прежнего) || lp(toSignPub))
```

`version` это версия состояния, которая ввела передачу.

**Проверка состояния** (`verifyGroupState`), по порядку:

| # | Проверка | Ошибка |
| --- | --- | --- |
| 1 | форма конверта, размер, `v = 1`, поля и их форматы, порядок и уникальность `members`, `prev` только у версии > 1 | `malformed`, `too-large`, `unsupported-version` |
| 2 | `serverId` равен ожидаемому | `wrong-server` |
| 3 | `chatId` равен ожидаемому | `wrong-chat` |
| 4 | если задан ожидаемый хэш (из запечатанного ключа): `stateHash` равен ему | `state-mismatch` |
| 5 | у каждого участника `userId` из `signPub`, ключ допустим | `user-id-mismatch`, `invalid-key` |
| 6 | `chatId` выводится из `creator` (раздел 14.1) | `bad-chain` |
| 7 | цепочка: начиная с создателя, у каждой передачи `version` строго растёт, больше 1 и не больше версии состояния, `to` выводится из `toSignPub`, `to` не текущий владелец, подпись прежнего владельца верна | `bad-chain` |
| 8 | `owner` это конец цепочки | `bad-chain` |
| 9 | `owner` входит в `members` | `malformed` |
| 10 | `by` это подписант версии: владелец после всех передач с `version` меньше версии состояния (передачу, введённую этой версией, подписывает и саму версию прежний владелец) | `not-owner` |
| 11 | подпись конверта ключом подписанта | `bad-signature` |

Если передано предыдущее принятое состояние `prev`, дополнительно:

| # | Проверка | Ошибка |
| --- | --- | --- |
| 12 | тот же создатель и `nonce` | `invalid-transition` |
| 13 | `version = prev.version + 1` | `invalid-transition` |
| 14 | `prev` равен `stateHash` предыдущего | `invalid-transition` |
| 15 | `transfers` продолжает прежнюю цепочку без изменений и добавляет не больше одной записи, и только с `version`, равной версии состояния | `bad-chain` |
| 16 | `by` равен `owner` предыдущего состояния | `not-owner` |
| 17 | `epoch` равна прежней или больше на 1 | `invalid-transition` |
| 18 | если кто-то из прежних участников исчез, `epoch = prev.epoch + 1` | `invalid-transition` |
| 19 | ключи оставшихся участников не изменились | `invalid-transition` |

Новичок (или восстановленное устройство) проверяет первое увиденное состояние без `prev`, по встроенной цепочке и хэшу из запечатанного ключа. Остаточный риск: бывший владелец, уже передавший группу, может подписать версию с более короткой цепочкой, и новичок её примет, если сервер её отдаст. От этого защищает сервер, который принимает смену состояния только от текущего владельца и только при совпадении версии; участник, уже видевший передачу, такую версию отвергнет (п. 15).

### 14.4. Зашифрованное состояние (то, что хранит сервер)

```
смещение  длина  поле
0         3      magic = "FCS" (46 43 53)
3         1      format = 0x01
4         4      epoch, u32
8         4      version, u32
12        8      serverTag (раздел 6.1)
20        8      chatTag (раздел 6.1)
28        12     nonce (случайный)
40        N+16   AES-256-GCM(encKey эпохи, nonce, plaintext, AAD)

AAD       = заголовок(28) || lp(serverId) || lp(chatId)
plaintext = u32(len) || JSON конверта {"payload","sig"} (len байт) || нули до кратного 256 (минимально)
```

Разбор (`openGroupState`): длина ≤ 131072, `≥ 56 + 256` и `(длина − 56)` кратно 256 (`too-large`, `malformed`); magic (`malformed`); format (`unsupported-version`); эпоха равна эпохе ключа (`wrong-epoch`); `serverTag` (`wrong-server`); `chatTag` (`wrong-chat`); GCM (`wrong-key`); длина и нулевое минимальное дополнение (`malformed`); затем проверка раздела 14.3; наконец версия и эпоха из заголовка равны подписанным (`malformed`). `readGroupStateHeader` читает эпоху и версию до расшифровки, чтобы выбрать ключ.

### 14.5. Изменения и что делает участник

Построители в `group-ops.ts` подписывают новую версию, проверяют её против предыдущей теми же правилами, что получатель, шифруют и запечатывают секрет:

| Действие | Эпоха | Секрет | Ключи получают |
| --- | --- | --- | --- |
| `createGroup` | 0 | новый | все участники, включая владельца (его другие устройства) |
| `renameGroup` | та же | прежний | никто |
| `addGroupMembers`, `history: true` | та же | прежний | только новички; они читают переписку текущей эпохи |
| `addGroupMembers`, `history: false` | +1 | новый | все |
| `removeGroupMembers` | +1 | новый | оставшиеся; владельца удалить нельзя |
| `transferGroupOwnership` | та же | прежний | никто; версию подписывает прежний владелец |

`groupStateActions(prev, next, me)` возвращает: `member`, `removed` (был и больше не участник: перестать отправлять, история только для чтения), `isOwner`, `newEpoch`, `needKey` (участник при новой эпохе ждёт свой ключ, прежде чем отправлять), `added`, `removedMembers`, `renamed`, `ownerChanged`. `compareGroupMembers(state, serverMembers)` сравнивает подписанный состав со списком доставки сервера.

## 15. Запечатанный ключ эпохи

### 15.1. HPKE

RFC 9180, режим base, набор: KEM `0x0020` DHKEM(X25519, HKDF-SHA256), KDF `0x0001` HKDF-SHA256, AEAD `0x0002` AES-256-GCM. Ключ получателя это его `boxPub`/`boxSecret` (раздел 3.2). Эфемерный ключ: `DeriveKeyPair(32 случайных байт)`. Нулевой результат X25519 отвергается (`invalid-key`). Реализация проверена на векторах RFC 9180 (`hpke-rfc9180.json`), включая 1000 последовательных шифрований и экспорт секрета.

### 15.2. Конверт group-key

Конверт вида `group-key`, подписан подписантом состояния, на которое ссылается (`by` этого состояния):

```json
{"v":1,"serverId":"…","chatId":"…","epoch":1,"recipient":"<userId>","stateVersion":3,
 "stateHash":"<b64url 32>","by":"<userId>","enc":"<b64url 32>","ct":"<b64url 48>"}
```

```
info = "fc/v1/group-key\n" || lp(serverId) || lp(chatId) || u32(epoch) || lp(recipient)
       || u32(stateVersion) || lp(stateHash)
enc, ct = HPKE.Seal(pkR = boxPub получателя, info, aad = пусто, plaintext = секрет эпохи)
```

Все поля, от которых зависит смысл ключа, входят в `info`: перенесённый в другой чат, эпоху, состояние или другому участнику шифртекст не откроется, даже если подменивший заново подпишет конверт своим ключом.

### 15.3. Открытие и проверка

`openGroupKey(env, me, {serverId})`: форма и `v` (`malformed`, `unsupported-version`); `serverId` (`wrong-server`); `recipient = me.userId` (`wrong-recipient`); HPKE.Open (`wrong-key`). Подпись проверяется после того, как получено и проверено состояние: `verifyGroupKey(key, state)` сверяет `chatId` (`wrong-chat`), версию и хэш (`state-mismatch`), эпоху (`wrong-epoch`), `by = state.by` (`not-owner`) и подпись (`bad-signature`). `acceptGroupKey` делает всё сразу: открывает ключ, выводит `encKey`, расшифровывает состояние версии `stateVersion`, проверяет его с ожидаемым хэшем и проверяет подпись ключа. `readGroupKey` читает открытые поля без расшифровки (для сортировки и маршрутизации). `parseSealedGroupKey(text)` разбирает строку ключа из `GET /v1/keys` (JSON конверта) и бросает `malformed`, если это не JSON.

## 16. Вложения

### 16.1. Ключ и части

- На каждый файл (включая пересылку) новый `blobId` (16 случайных байт, base32) и новый ключ (32 случайных байта).
- Файл режется на части по `partSize = 4194304` байт; `parts = ceil(size / partSize)`, у пустого файла одна пустая часть. Номера частей с 0.

```
часть i = AES-256-GCM(key, nonce = 00×8 || u32(i), plaintext_i,
                      AAD = "fc/v1/blob\n" || lp(blobId, сырые 16 байт) || u32(i) || u32(parts))
```

- Длина шифртекста части: `partSize + 16`, у последней `size − (parts − 1) × partSize + 16`.
- Одна и та же часть всегда шифруется в одни и те же байты (nonce это номер), поэтому возобновлённая загрузка шлёт то же самое и ключ никогда не шифрует разные данные под одним nonce. Клиент шифрует неизменяемую копию файла.

### 16.2. Расшифровка

`decryptBlobPart(blob, i, ct)`: описатель проверяется (`malformed`); длина не совпадает с ожидаемой: `malformed` (обрезанная часть); GCM: `wrong-key` (изменённые байты, часть с другим номером, часть другого файла, другое число частей). Обрезание файла по границе части тоже обнаруживается: число частей подписано в описателе, а оно входит в AAD. API работает по одной части, весь файл в памяти не нужен.

### 16.3. Описатель

```json
{"blob":{"id":"<blobId>","key":"<b64url 32>","parts":1,"partSize":4194304,"size":1000},
 "name":"photo.jpg","mime":"image/jpeg","kind":"image","w":800,"h":600,"thumb":"<b64url JPEG>"}
{"blob":{…},"name":"voice.m4a","mime":"audio/mp4","kind":"voice","dur":4200,"peaks":[0,37,…]}
```

Строгая проверка при получении (`validateAttachment`, ошибка `malformed`):

- `blob.id`: строго base32 16 байт (никаких `.`, `/`, заглавных букв; путь на сервере строится только из него); `blob.key` base64url 32 байта; `partSize` из ряда {4194304}; `size` целое ≥ 0, не больше лимита (2 ГиБ, либо меньший лимит сервера, переданный вызывающим); `parts = ceil(size / partSize)`, 1 для пустого файла.
- `name`: 1-128 кодовых точек, ≤ 255 байт, без управляющих и bidi-символов, без пробелов по краям, без `/` и `\`, не `.` и не `..`.
- `mime`: строчный `type/subtype` без параметров. Для `image` один из `image/jpeg`, `image/png`, `image/webp`, `image/gif`; для `voice` один из `audio/mp4`, `audio/webm`, `audio/ogg`; для `file` любой допустимой формы (показывать файл по нему нельзя, только предлагать скачать).
- `kind`: `image`, `voice` или `file`.
- `w`, `h`: целые 1-65535; обязательны у `image`, допустимы у `file`, запрещены у `voice`.
- `thumb`: base64url JPEG (первые байты `FF D8 FF`) не больше 4096 байт; у `image` и `file`.
- `dur` (миллисекунды, 0-86400000) и `peaks` (ровно 64 целых 0-255): обязательны у `voice` и запрещены у остальных.
- Неизвестные поля игнорируются и в нормализованный описатель не попадают.

Те же правила для своего описателя перед отправкой: `checkAttachmentInput` (ошибка `invalid-argument`). Списки типов экспортируются как `IMAGE_TYPES` и `VOICE_TYPES`.

Перед декодированием картинки клиент читает её размеры (предел 40 мегапикселей); это не часть протокола.

## 17. Архив `.fcarchive`

### 17.1. Формат

```
заголовок (36 байт) = "FCA" || 0x01 || salt(16) || check(16)
archiveKey          = HKDF(selfKey, "fc/v1/archive" || salt)
check               = HKDF(archiveKey, "fc/v1/archive-check")[0..16]
блок i              = AES-256-GCM(archiveKey, nonce = 00×8 || u32(i), plaintext_i,
                                  AAD = заголовок(36) || u32(i) || u8(last))
файл                = заголовок || блок 0 || блок 1 || …
```

- Открытый текст (поток записей, раздел 17.3) режется на блоки по 1 МиБ; каждый блок, кроме последнего, ровно 1 МиБ открытого текста (1048592 байт шифртекста). Последний блок короче или равен 1 МиБ, может быть пустым (16 байт), и только у него `last = 1`.
- Соль случайная на каждый экспорт, поэтому у каждого архива свой ключ.
- Обрезание по границе блока ловит флаг `last`, перестановку ловит номер блока в nonce и AAD, подмену заголовка ловит заголовок в AAD.

### 17.2. Чтение

Чтение идёт потоком: читатель держит не больше одного блока и одной записи. Блок точно не последний, если после него в буфере есть ещё байты. Ошибки: не архив (`malformed`), формат новее (`unsupported-version`), `check` не совпал (`wrong-identity`: «архив создан другой идентичностью»), блок не расшифровался, хвост короче 16 байт, поток кончился внутри записи (`malformed`).

### 17.3. Записи

```
запись = u16(type) || u32(len) || data(len)
```

`type` 1-65535 выбирает клиентское ядро (0 зарезервирован), `len` ≤ 16 МиБ; записи идут подряд и могут пересекать границы блоков. Что лежит в записях (серверы без паролей, контакты, чаты с секретами эпох, сообщения, вложения), определяет клиентское ядро; файлы больше 16 МиБ оно режет на несколько записей.

API: `createArchiveWriter(keys)` даёт `header` и методы `write(type, data)` и `finish()`, которые возвращают готовые блоки; `createArchiveReader(keys)` с методами `push(chunk)` и `finish()`; `readArchive(source, keys)` это асинхронный генератор записей. `keys` это любой объект с `selfKey`, например `IdentityKeys`.

## 18. Наборы стикеров

### 18.1. Что шифруется

Ничего: набор публикуется для всех участников сервера, ключа у набора нет. Манифест и файлы лежат на сервере открыто, их видит тот, у кого есть доступ к серверу или его папке данных. Подлинность обеспечивают подпись загрузившего и хэш каждого файла. Сообщение со стикером шифруется, как любое `msg`.

### 18.2. Имя файла

`hash32 = base32(SHA-256(файл)[0..20])`: 32 символа строчного base32 без дополнения. Сервер принимает файл, только если его байты дают это имя; клиент проверяет то же самое и размер из манифеста до показа. Типы: `webp` (WebP, статичный или анимированный, до 524288 байт) и `tgs` (gzip Lottie JSON, до 131072 байт).

### 18.3. Манифест: конверт `sticker-pack`

Подписанный конверт (раздел 4.1) вида `sticker-pack`, подпись ключом подписи идентичности загрузившего, payload до 65536 байт:

```json
{"v":1,"packId":"<base32 16 байт>","serverId":"<serverId>","author":"<userId>","name":"Котики","created":1767225600000,
 "stickers":[{"file":"<hash32>","type":"webp","size":31544,"emoji":"😺","w":512,"h":512}]}
```

- `packId` выбирает загрузивший (случайные 16 байт). `serverId`: сервер, где набор опубликован; манифест с другим `serverId` отвергается (`wrong-server`), поэтому его нельзя перенести на другой сервер.
- `author` равен `userId` подписавшего (`user-id-mismatch` иначе).
- `name`: 1-64 кодовых точки, правила имени профиля.
- `stickers`: 1-200 элементов, файлы не повторяются, сумма `size` не больше 52428800. `w`, `h`: целые 1-1024. `emoji`: правила эмодзи реакции.
- Порядок ключей при записи указан в примере. Проверка идёт по принятым байтам, как у остальных конвертов.

API: `createStickerPackEnvelope(keys, input)`, `readStickerPackHeader(envelope)` (узнать `author` до проверки), `verifyStickerPackEnvelope(envelope, identity, {serverId, packId?})`, `stickerFileHash(bytes)`, `stickerFileMatches(bytes, sticker)`.

### 18.4. Что клиент делает с файлом

Каждый файл считается враждебным:

- WebP: сначала читается заголовок (`VP8`, `VP8L` или `VP8X`), стороны не больше 1024, флаг анимации; потом картинка показывается через `<img>` из `blob:` или первый кадр через `createImageBitmap`. SVG и HTML из файлов никогда не показываются.
- `.tgs`: распаковка gzip потоком с пределом 1 МиБ, строгий разбор JSON, затем очистка: удаляются выражения (строковые `x`), все строки, похожие на адрес (`http:`, `https:`, `data:`, `blob:`, `javascript:`, `//`), картинки, звуки и шрифты из `assets`, слои текста, картинок, звука и камеры, `fonts`, `chars`, `markers`. Пределы: частота кадров до 120, длительность до 10 секунд, стороны до 1024, слоёв до 500, слоёв после раскрытия прекомпозиций до 2000, узлов дерева до 300000, прекомпозиция не может ссылаться на себя. Показывается лёгкой сборкой `lottie-web` (только SVG, без поддержки выражений).
- Импорт `.zip` (только для публикации своего набора): записи из центрального каталога, без шифрования, ZIP64 и многотомности, методы «без сжатия» и deflate, пути без `..`, абсолютных путей, букв дисков, обратной косой черты и NUL, диапазоны данных внутри файла и без перекрытий, не больше 1000 записей, файл до 524288 байт, всего до 52428800 байт распакованного, сжатие не сильнее 100:1, распаковка останавливается на заявленном размере, CRC-32 должен совпасть, архив внутри архива отвергается.
