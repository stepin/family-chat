# API сервера `fcd`

Документ описывает HTTP API сервера `fcd` версии 0.1 (протокол `1`) так, чтобы по нему одному можно было написать клиент. Форматы шифрования событий, состояния группы, запечатанных ключей и вложений описаны в `docs/PROTOCOL.md`: для сервера всё это непрозрачные байты.

Что есть: вступление по приглашению или коду администратора, сведения о приглашении до вступления, устройства, участники, профили и аватары, отзыв идентичности, личные чаты (в том числе чат с самим собой, «Избранное»), группы с состоянием, эпохами и запечатанными ключами, служебные записи сервера, события с длинным запросом, вложения, подписка на уведомления, администрирование, HTTPS со своими файлами сертификата, удаление события «у всех» (`DELETE /v1/chats/<id>/events/<gseq>`, раздел 5.6), наборы стикеров (раздел 8a), подсказка «без уведомления» для служебных событий (заголовок `X-FC-Push`, раздел 5.3), приём «Поделиться» без service worker (раздел 12.4), проверка сервера (раздел 10a).

## 1. Общие правила

### 1.1. Адрес, формат, CORS

- Все запросы идут по адресу `/v1/...` того же сервера, который отдаёт клиент. Порт по умолчанию 8787. HTTPS даёт обратный прокси или сам сервер (раздел 12.2).
- Тела запросов и ответов JSON в UTF-8 (`Content-Type: application/json`), кроме: тела `POST /v1/chats/<chatId>/events`, тела `PUT /v1/me/avatar`, тела частей вложений (`PUT /v1/blobs/...`) и файлов стикеров (`PUT /v1/packs/<packId>/files/<hash>`): там сырые байты. Ответы `GET /v1/chats/<id>/state/<version>` и `GET /v1/blobs/<id>/<part>` тоже сырые байты (`application/octet-stream`), аватар отдаётся как `image/jpeg` или `image/webp`. `Content-Type` запроса сервер не проверяет.
- Каждый ответ API несёт заголовки CORS: `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS`, `Access-Control-Allow-Headers: Authorization, Content-Type, Idempotency-Key, X-FC-Epoch, X-FC-Push`, `Access-Control-Expose-Headers: Retry-After`, `Access-Control-Max-Age: 86400`. Запрос `OPTIONS` на любой путь `/v1/...` отвечает 204. Cookie сервер не ставит и не читает.
- Заголовки безопасности на каждом ответе описаны в разделе 12.1. Главное для клиента: ответы API (кроме аватаров) несут `Cache-Control: no-store`.
- Время везде в миллисекундах от 1970-01-01 UTC (целое число) и всегда по часам сервера.

### 1.2. Кодировки и идентификаторы

| Что | Формат |
| --- | --- |
| двоичные значения в JSON (ключи, подписи, тела событий, состояние группы, `nonce`, токен, хэш аватара) | base64url **без** `=` (RFC 4648, раздел 5) |
| запечатанный ключ группы (`key` в `POST /v1/chats`, `PUT /v1/chats/<id>/state`, `GET /v1/keys`) | непрозрачная строка; протокол кладёт туда сериализованный конверт `group-key` (`docs/PROTOCOL.md`), сервер хранит и отдаёт её дословно |
| base32 | алфавит RFC 4648 `a-z2-7`, **строчные** буквы, без `=` |
| `userId` | base32 первых 16 байт SHA-256(`signPub`), 26 символов |
| `devId` | base32 10 случайных байт, 16 символов; создаёт клиент |
| `msgId` (он же `Idempotency-Key`) | base32 16 случайных байт, 26 символов; создаёт клиент |
| `chatId` | base32 16 байт, 26 символов. Личный чат: формула раздела 5.1. Группа: 16 случайных байт, выбирает клиент |
| `blobId` | base32 16 случайных байт, 26 символов; создаёт клиент |
| номер части вложения | десятичное число 0-9999 без ведущих нулей |
| `version` | версия состояния группы, целое ≥ 1, растёт на единицу |
| `serverId` | непрозрачная строка из `/v1/hello` (сейчас base64url 16 байт, 22 символа); клиент сравнивает и подставляет её дословно |
| токен устройства | base64url 32 случайных байт, 43 символа |
| код приглашения | base32 16 случайных байт, 26 символов |
| `gseq` | целое ≥ 1, сквозной номер записи журнала сервера (события участников и служебные записи), растёт на единицу |
| `epoch` | u32, у личного чата всегда 0; у группы задаёт создатель и меняет владелец |

Декодеры сервера строгие: base32 только строчными, base64url без `=`, длина ровно ожидаемая, неиспользуемые младшие биты последнего символа нулевые. Идентификатор в другом виде (заглавные буквы, `=`, лишний символ) сервер отвергает с 400. Поэтому идентификаторы можно сравнивать как строки. Числа в пути (`version`, номер части) только десятичные без знака и ведущих нулей (`01` даёт 400).

### 1.3. Вход

Все запросы, кроме `GET /v1/hello`, `POST /v1/join`, `POST /v1/invites/check`, `POST /v1/auth/challenge`, `POST /v1/auth/device`, `POST /v1/revoke`, требуют заголовок

```
Authorization: Bearer <токен устройства>
```

Токен выдаётся один раз (ответ `join` или `auth/device`), сервер хранит только его SHA-256. Токен бессрочный; он перестаёт действовать, когда устройство входит заново с тем же `devId`, когда участника исключают или когда участник отзывает свою идентичность.

Ответы на ошибку входа:

- 401 `unauthorized`: заголовка нет, токен неизвестен или заменён. В ответе `WWW-Authenticate: Bearer`. Клиент входит заново подписью (`auth/challenge` + `auth/device`, раздел 3).
- 403 `removed`: участник исключён из семьи. Заново войти нельзя; локальная история остаётся.
- 403 `revoked`: владелец отозвал эту идентичность (раздел 4.5). Войти с ней больше нельзя никогда.

### 1.4. Ошибки

Тело любой ошибки:

```json
{"error": "<код>", "message": "<текст для разработчика, по-английски>"}
```

Иногда добавляются поля (например `epoch`, `limit`, `rev`, `version`); они указаны у конкретных запросов. Текст `message` не для показа пользователю, клиент различает ошибки по `error` и статусу.

| Статус | Коды `error` | Когда |
| --- | --- | --- |
| 400 | `bad_request`, `bad_member`, `unknown_avatar`, `bad_image` | неверный JSON, поле, идентификатор, заголовок; повреждённый конверт; участник группы не из семьи; аватар профиля не загружен; картинка не JPEG и не WebP |
| 401 | `unauthorized`, `bad_signature`, `bad_nonce` | нет или неверный токен; неверная подпись; неизвестный, использованный или просроченный `nonce` |
| 403 | `removed`, `revoked`, `not_member`, `not_owner`, `not_admin`, `peer_removed`, `invalid_invite`, `invalid_code`, `not_author` | исключён; идентичность отозвана; не участник чата; не владелец группы или вложения; не администратор; собеседник исключён или отозвал идентичность; неизвестное приглашение; неверный или уже использованный код администратора; удалить событие может только его отправитель или владелец группы (5.6) |
| 404 | `not_found`, `chat_not_found`, `unknown_user`, `blob_not_found`, `event_not_found` | нет такого пути, приглашения, версии состояния, аватара; нет такого чата; нет такого участника; нет такого вложения или части; нет такого события участника в этом чате (5.6) |
| 405 | `method_not_allowed` | путь есть, метода нет |
| 409 | `already_member`, `stale_rev`, `stale_version`, `epoch_mismatch`, `idempotency_conflict`, `push_disabled`, `cannot_remove_self`, `chat_exists`, `owner_cannot_leave` | см. запросы |
| 410 | `invite_used`, `invite_expired`, `expired` | приглашение уже использовано или просрочено; событие уже удалено по сроку хранения (5.6) |
| 413 | `too_large` | тело больше предела; в ответе `"limit": <байт>` |
| 429 | `rate_limited` | слишком много неверных кодов или подписей с адреса; заголовок `Retry-After: <секунд>` |
| 500 | `internal` | ошибка сервера (подробности в журнале сервера) |
| 507 | `storage_full` | на диске сервера мало места |

### 1.5. Ограничение частоты

Неверный код приглашения (в `join` и в `invites/check`), неверный код администратора, неверная подпись (`bad_signature`, в том числе в `revoke`) и неверный `nonce` (`bad_nonce`) засчитываются адресу клиента. После 10 таких ошибок за 60 секунд все запросы `POST /v1/join`, `POST /v1/invites/check`, `POST /v1/auth/device` и `POST /v1/revoke` с этого адреса получают 429 `rate_limited` (даже с верным кодом), пока самая старая ошибка не выйдет из окна. `Retry-After` говорит, через сколько секунд.

Адрес клиента это адрес TCP-соединения. Если в настройках сервера `trust_forwarded_for = true` (только за обратным прокси), берётся последний (самый правый) адрес из `X-Forwarded-For`.

### 1.6. Подписанные конверты

Конверт это JSON-объект

```json
{"payload": "<base64url>", "sig": "<base64url>"}
```

- `payload`: base64url точных байтов UTF-8 JSON-документа. Сервер разбирает и проверяет именно эти байты, ничего не переупорядочивает и хранит конверт как есть. Декодированный `payload` не длиннее 8192 байт.
- `sig`: подпись Ed25519 (64 байта) над байтами `utf8("fc/v1/" + kind + "\n")`, за которыми сразу идут байты `payload`. `kind` один из `identity`, `profile`, `auth`, `revoked`. Проверка строгая (`verify_strict`).
- Лишние поля в `payload` сервер пропускает.

| `kind` | `payload` | Чем проверяется подпись | Что ещё проверяет сервер |
| --- | --- | --- | --- |
| `identity` | `{"v":1,"userId":"…","signPub":"…","boxPub":"…","created":<ms>}` | `signPub` из самого `payload` | `v == 1`; `signPub` и `boxPub` ровно 32 байта (Ed25519 и X25519, сырые); `userId` равен base32(SHA-256[signPub](0..16)); `created` целое |
| `profile` | `{"v":1,"userId":"…","name":"…","avatar":null,"rev":<int>,"updated":<ms>}` | сохранённый `signPub` участника | `v == 1`; `userId` свой; `name` от 1 до 64 символов (Unicode), не из одних пробелов (U+FEFF тоже считается пробелом), без управляющих символов C0, DEL, C1 и символов управления направлением текста (U+061C, U+200E, U+200F, U+202A-U+202E, U+2066-U+2069), без непарных суррогатов (как в `packages/protocol`, `docs/PROTOCOL.md` 4.3); `avatar` по правилам раздела 4.3; `rev` целое ≥ 0 и больше сохранённого; `updated` целое |
| `auth` | `{"v":1,"userId":"…","serverId":"…","nonce":"…","devId":"…"}` | сохранённый `signPub` участника | `serverId` равен серверному; `nonce` выдан этим сервером, не использован и не старше 2 минут; `devId` в формате раздела 1.2 |
| `revoked` | `{"v":1,"userId":"…","revokedAt":<ms>}` | сохранённый `signPub` участника `userId` | `v == 1`; `userId` в формате раздела 1.2 и есть на сервере; `revokedAt` целое ≥ 0 (время по часам клиента, сервер его с часами не сравнивает) |

Повреждённый конверт (не base64url, не JSON, не те поля) даёт 400 `bad_request`; неверная подпись даёт 401 `bad_signature`.

### 1.7. Пределы

| Что | Предел |
| --- | --- |
| тело события | от 1 до 262144 байт (256 КиБ) |
| тело JSON-запроса | 65536 байт; у `POST /v1/chats` и `PUT /v1/chats/<id>/state` 1048576 байт (1 МиБ) |
| состояние группы | от 1 до 262144 байт (до кодирования base64) |
| запечатанный ключ | строка от 1 до 8192 байт (UTF-8) |
| участников в группе | от 1 до 100 |
| аватар | от 1 до 262144 байт, JPEG или WebP |
| часть вложения | от 1 до 4194560 байт (4 МиБ + 256 байт на шифрование) |
| вложение целиком (сумма частей) | `maxFileMb` × 1048576 + 65536 байт (поле `maxBlobBytes` в `/v1/hello`) |
| `limit` в `GET /v1/events` | 1-500, по умолчанию 500 (больше 500 молча уменьшается до 500) |
| `limit` в `GET /v1/chats/<id>/events` | 1-500, по умолчанию 200 |
| `limit` в `GET /v1/keys` | 1-500, по умолчанию 500 |
| `wait` в `GET /v1/events` | 0-30 секунд, по умолчанию 0 (больше 30 молча уменьшается до 30) |
| сумма тел событий в одном ответе | около 4 МиБ (до кодирования base64): ответ может содержать меньше `limit` записей, тогда `more: true`; одна запись отдаётся всегда |
| срок приглашения | 7 суток |
| срок `nonce` | 2 минуты, одно использование |
| имя в профиле | 64 символа |

## 2. Сервер

### `GET /v1/hello`

Без входа. Ответ 200:

```json
{
  "protocol": 1,
  "server": "fcd",
  "version": "1.0.0",
  "commit": "3208eeb2c67a",
  "serverId": "q8Jb3kVf0w2Xy7HnT1sZ9A",
  "familyName": "Семья",
  "retentionDays": 90,
  "maxFileMb": 200,
  "push": true,
  "vapidPublicKey": "BOr…",
  "time": 1794787200000,
  "maxEventBytes": 262144,
  "maxPartBytes": 4194560,
  "maxBlobBytes": 209780736,
  "maxAvatarBytes": 262144,
  "maxStateBytes": 262144,
  "maxSealedKeyBytes": 8192,
  "maxGroupMembers": 100,
  "adminCodeActive": false,
  "offerSetup": false
}
```

- `commit`: коммит, из которого собран сервер (до 12 шестнадцатеричных знаков), или `null`, если неизвестен. То же показывает `fcd --version`.
- `vapidPublicKey`: открытый ключ VAPID (несжатая точка P-256, 65 байт, base64url) для `PushManager.subscribe({applicationServerKey})`; `null`, если `push` выключен.
- `adminCodeActive`: `true`, пока код администратора ещё не использован (на сервере нет администратора). Клиент по нему выбирает экран: «введите код администратора» или «нужно приглашение».
- `time`: часы сервера; клиент может показать предупреждение о сильном расхождении, но порядок от часов клиента не зависит.
- `maxPartBytes`, `maxBlobBytes`, `maxAvatarBytes`, `maxStateBytes`, `maxSealedKeyBytes`, `maxGroupMembers`: пределы раздела 1.7. `maxFileMb` остаётся для показа пользователю («файлы до 200 МБ»); проверять размер вложения лучше по `maxBlobBytes`.
- `offerSetup`: сервер запущен с `--offer-setup`; первый экран клиента предлагает «Настроить для своей семьи», даже когда `adminCodeActive` уже `false` (настройка семьи на другом сервере).

## 3. Вступление и устройства

### `POST /v1/join`

Вступление в семью: по одноразовому приглашению или по коду администратора (первый вход). Без входа. Тело:

```json
{
  "invite": "<код приглашения>",
  "identity": {"payload": "…", "sig": "…"},
  "profile": {"payload": "…", "sig": "…"},
  "devId": "aaaqeayeaudaocaj"
}
```

Вместо `invite` для первого администратора передаётся `"adminCode": "<код из журнала сервера>"`. Ровно одно из двух полей, иначе 400.

- Код приглашения сервер принимает без учёта регистра и пробелов по краям. Код администратора тоже без учёта регистра, дефисов и пробелов; буквы `O`, `I`, `L` читаются как `0`, `1`, `1`.
- `identity` это конверт `identity`, `profile` это конверт `profile` того же `userId`, подписанный тем же ключом. `avatar` в профиле при вступлении должен быть `null` (аватар загружается после вступления, раздел 4.4), иначе 400.
- Кто вошёл по коду администратора, становится администратором; код после этого перестаёт действовать (`adminCodeActive` становится `false`). Новый код выдаёт команда `fcd reset-admin-code --data <DIR>` при остановленном сервере, и следующий вошедший по нему тоже становится администратором.
- Приглашение после успешного входа помечается использованным.
- Если пользователь с этим `userId` был исключён, вступление по новому приглашению возвращает его в семью; прежние устройства остаются недействительными. Отозванная идентичность вернуться не может (403 `revoked`).

Ответ 200:

```json
{"token": "<43 символа base64url>", "userId": "mmg42klgyqzwneiskrelxms3j4", "devId": "aaaqeayeaudaocaj", "admin": true}
```

Ошибки:

| Статус | `error` | Причина |
| --- | --- | --- |
| 400 | `bad_request` | тело, `devId`, конверты не по формату; нет или оба поля кода; `avatar` не `null` |
| 401 | `bad_signature` | подпись `identity` или `profile` неверна |
| 403 | `invalid_invite` | приглашение неизвестно или отозвано (после очистки и просроченное) |
| 403 | `invalid_code` | код администратора неверен или уже использован |
| 403 | `revoked` | эта идентичность отозвана |
| 409 | `already_member` | этот `userId` уже в семье: нужен `auth/device` |
| 410 | `invite_used` | приглашение уже использовано |
| 410 | `invite_expired` | срок приглашения истёк |
| 413 | `too_large` | тело больше 64 КиБ |
| 429 | `rate_limited` | раздел 1.5 |
| 507 | `storage_full` | мало места на диске |

Сначала проверяются формат и подписи, затем код; код расходуется только если всё остальное верно. Ошибки 401, 403 `invalid_invite`/`invalid_code` и 410 этого запроса засчитываются в ограничение частоты.

Ссылка-приглашение: `https://<адрес сервера>/#invite=<код>`. Сервер её не строит и не видит фрагмент; клиент собирает ссылку из кода (ответ `POST /v1/admin/invites`) и своего адреса и после чтения убирает фрагмент из адресной строки.

### `POST /v1/invites/check`

Сведения о приглашении до вступления: экран «Вас приглашает Мама в семью «Ивановы»» или «Это приглашение уже использовано». Без входа. Код передаётся в теле, а не в адресе, чтобы не попадать в журналы прокси. Тело:

```json
{"invite": "<код приглашения>"}
```

Код читается так же, как в `join` (без учёта регистра и пробелов по краям). Ответ 200:

```json
{
  "status": "valid",
  "familyName": "Ивановы",
  "createdBy": {"userId": "mmg42klgyqzwneiskrelxms3j4", "name": "Мама", "gender": "f"},
  "createdAt": 1794787200000,
  "expiresAt": 1795392000000
}
```

- `status`: `valid` (можно вступать), `used` (уже использовано), `expired` (срок истёк, но ежечасная очистка его ещё не удалила; после очистки ответ 403 `invalid_invite`).
- `createdBy.name`: имя из текущего подписанного профиля выпустившего администратора; `null`, если профиля нет. Подписанный профиль клиент получит после вступления; до него это непроверенная подсказка.
- `createdBy.gender`: `"m"` или `"f"` из того же профиля (поле `gender`, PROTOCOL.md 4.3); `"m"`, если профиля или поля нет. Нужен приглашению: «Вас пригласил» или «Вас пригласила».
- Запрос ничего не меняет, приглашение не расходуется.

Ошибки: 400 `bad_request` (тело), 403 `invalid_invite` (неизвестный код, засчитывается в ограничение частоты), 413, 429 `rate_limited` (общий счётчик с `join`, раздел 1.5).

### `POST /v1/auth/challenge`

Без входа, тело пустое. Ответ 200:

```json
{"nonce": "<base64url 32 байт, 43 символа>", "expiresAt": 1794787320000}
```

`nonce` действует 2 минуты и один раз. Сервер держит не больше 1000 невыданных вызовов; самые старые вытесняются.

### `POST /v1/auth/device`

Новое устройство существующего участника или вход заново после 401 (восстановление по фразе, потерянный токен). Без входа. Тело это конверт `auth`:

```json
{"payload": "<base64url от {\"v\":1,\"userId\":\"…\",\"serverId\":\"…\",\"nonce\":\"…\",\"devId\":\"…\"}>", "sig": "…"}
```

`nonce` копируется из ответа `auth/challenge` дословно, `serverId` из `/v1/hello`.

Ответ 200, как у `join`:

```json
{"token": "…", "userId": "…", "devId": "…", "admin": false}
```

- Если у участника уже есть устройство с этим `devId`, оно заменяется: старый токен перестаёт действовать, подписка на уведомления этого устройства удаляется.
- `nonce` расходуется при любой попытке, даже неудачной.

Ошибки:

| Статус | `error` | Причина |
| --- | --- | --- |
| 400 | `bad_request` | конверт не по формату; `serverId` чужой |
| 401 | `bad_nonce` | `nonce` неизвестен, использован или просрочен |
| 401 | `bad_signature` | подпись неверна |
| 403 | `removed` | участник исключён |
| 403 | `revoked` | идентичность отозвана |
| 404 | `unknown_user` | такого участника на сервере нет: нужно приглашение |
| 429 | `rate_limited` | раздел 1.5 |

## 4. Участники, профиль, аватар, отзыв

### 4.1. `GET /v1/users`

Все участники семьи, включая исключённых и отозванных (их подписи нужны для старых сообщений). Отсортированы по `userId`. Ответ 200:

```json
{
  "users": [
    {
      "userId": "mmg42klgyqzwneiskrelxms3j4",
      "identity": {"payload": "…", "sig": "…"},
      "profile": {"payload": "…", "sig": "…"},
      "admin": true,
      "removed": false,
      "revoked": null
    }
  ]
}
```

- `identity` и `profile` это конверты в точности как их прислал владелец. `profile` может быть `null` только у данных, повреждённых на диске. Клиент сам проверяет подписи (`docs/PROTOCOL.md`).
- `revoked`: `null` или конверт `revoked` в точности как его прислал владелец (раздел 4.5). Клиент проверяет подпись ключом из `identity`, запоминает отзыв навсегда, перестаёт шифровать для этой идентичности и помечает её в интерфейсе.

### 4.2. `GET /v1/me`

Свой участник и текущее устройство. Ответ 200: те же поля, что у элемента `users`, плюс

```json
{"devId": "aaaqeayeaudaocaj", "push": false}
```

`push`: есть ли у этого устройства подписка на уведомления.

### 4.3. `PUT /v1/me/profile`

Тело это конверт `profile` (раздел 1.6). `rev` должен быть больше сохранённого. Ответ 200:

```json
{"profile": {"payload": "…", "sig": "…"}}
```

Поле `avatar` в `payload`:

- `null`: аватара нет;
- объект ровно с двумя ключами `{"sha256":"<base64url 32 байт>","type":"image/jpeg"|"image/webp"}`: SHA-256 байтов картинки и её тип, как их вернул `PUT /v1/me/avatar`. Лишний ключ, другой тип или хэш не из 32 байт дают 400 `bad_request` (та же форма, что в `docs/PROTOCOL.md` 4.3). Картинка с этим хэшем и типом должна быть загружена этим участником, иначе 400 `unknown_avatar`.

Ошибки: 400 `bad_request` (формат, чужой `userId`, имя длиннее 64 символов, пустое или с запрещёнными символами, `avatar` не по правилам), 400 `unknown_avatar`, 401 `bad_signature`, 409 `stale_rev` (в ответе `"rev": <сохранённый>`).

После успешной смены профиля сервер удаляет файлы аватаров этого участника, кроме названного в профиле и самого последнего загруженного.

### 4.4. Аватар

#### `PUT /v1/me/avatar`

Тело: байты картинки (от 1 до 262144 байт). Тип определяется по первым байтам: JPEG начинается с `FF D8 FF`, WebP с `RIFF`, четыре любых байта, `WEBP`. Заголовок `Content-Type` не важен. Сервер картинку не перекодирует и не разбирает: уменьшение и удаление EXIF делает клиент.

Ответ 200:

```json
{"sha256": "<base64url SHA-256 байтов>", "type": "image/jpeg"}
```

Этот объект клиент кладёт в поле `avatar` нового профиля и отправляет `PUT /v1/me/profile`. Пока профиль не сменён, участники видят прежний аватар. Сервер хранит не больше двух картинок участника: названную в текущем профиле и последнюю загруженную.

Ошибки: 400 `bad_image` (не JPEG и не WebP), 413 `too_large` (`"limit": 262144`), 507 `storage_full`.

#### `GET /v1/users/<userId>/avatar/<sha256>`

Картинка участника по хэшу из его профиля (`sha256` в base64url, как в профиле). Требует токен любого действующего участника семьи. Ответ 200 с телом-картинкой и заголовками `Content-Type: image/jpeg` или `image/webp`, `Cache-Control: private, max-age=31536000, immutable` (хэш в адресе, содержимое по адресу не меняется), `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; sandbox`, `X-Content-Type-Options: nosniff`.

`<img src>` не умеет передать `Authorization`, поэтому клиент скачивает картинку `fetch` с токеном, проверяет SHA-256 и показывает через `blob:`-адрес (CSP клиента разрешает `img-src blob:`).

Ошибки: 400 `bad_request` (неверный `userId` или хэш), 404 `not_found` (такой картинки у участника нет, например её уже заменили).

### 4.5. `POST /v1/revoke`

Отзыв идентичности её владельцем: потеря устройства, ключ мог утечь, участник переходит на новую идентичность. Токен не нужен: право даёт подпись ключом отзываемой идентичности, поэтому отозвать можно и с одной фразой восстановления, без устройства. Тело это конверт `revoked`:

```json
{"payload": "<base64url от {\"v\":1,\"userId\":\"…\",\"revokedAt\":1794787200000}>", "sig": "…"}
```

Ответ 204. Сразу после этого:

- все токены участника получают 403 `revoked`, его ждущие `GET /v1/events` заканчиваются 403 `revoked`;
- `auth/device` и `join` с этой идентичностью отвечают 403 `revoked`, навсегда;
- если он был администратором, перестаёт им быть;
- отправка в личный чат с ним отвечает 403 `peer_removed`;
- в `GET /v1/users` у него появляется `revoked` (конверт), в `GET /v1/admin/users` `revoked: true`;
- владельцы групп, где он состоит, получают служебную запись `member_revoked` (раздел 7). Из списков групп сервер его сам не убирает: это делает владелец сменой состояния и эпохи.

Повтор отзыва уже отозванной идентичности тоже отвечает 204 и ничего не меняет (хранится первый конверт).

Ошибки: 400 `bad_request` (конверт не по формату), 401 `bad_signature` (засчитывается в ограничение частоты), 404 `unknown_user`, 413, 429 `rate_limited`.

## 5. Чаты и события

### 5.1. Идентификатор личного чата

```
lo, hi = два userId, упорядоченные как строки (побайтно, по возрастанию)
chatId = base32( SHA-256( utf8("fc/v1/dm\n" + serverId + "\n" + lo + "\n" + hi) )[0..16] )
```

Строка хэшируется целиком, `\n` это байт 0x0A, префиксов длины нет. Пример (векторы и в `docs/vectors/dm.json`):

| Что | Значение |
| --- | --- |
| `signPub` A | байты 0x00..0x1f: `AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8` |
| `userId` A | `mmg42klgyqzwneiskrelxms3j4` |
| `signPub` B | байты 0x20..0x3f: `ICEiIyQlJicoKSorLC0uLzAxMjM0NTY3ODk6Ozw9Pj8` |
| `userId` B | `oln3om3moz4aai7yhwsmgvps5y` |
| `serverId` | `c2VydmVyLWlkLWV4YW1wbGU` |
| хэшируемая строка | `"fc/v1/dm\nc2VydmVyLWlkLWV4YW1wbGU\nmmg42klgyqzwneiskrelxms3j4\noln3om3moz4aai7yhwsmgvps5y"` |
| `chatId` | `lo2a5ewrojycetbvska5utmpxe` |

Личный чат создаётся первым событием: клиент вычисляет `chatId` и сразу делает `POST /v1/chats/<chatId>/events`. Сервер находит собеседника перебором участников (тот, для кого формула даёт этот `chatId`) и записывает `chats/<chatId>/meta.json`. Отдельного запроса «создать чат» нет.

**Чат с самим собой («Избранное»)** это личный чат, где оба участника один и тот же пользователь: `lo = hi = мой userId`, формула та же. Он же переносит сообщения между своими устройствами. В `GET /v1/chats` у него `kind: "dm"` и `members` из двух одинаковых `userId`. Его события доставляются всем устройствам владельца; уведомление получают все его устройства, кроме отправившего.

### 5.2. `GET /v1/chats`

Чаты, где я сейчас участник, по `chatId`. Ответ 200:

```json
{
  "chats": [
    {
      "chatId": "lo2a5ewrojycetbvska5utmpxe",
      "kind": "dm",
      "members": ["mmg42klgyqzwneiskrelxms3j4", "oln3om3moz4aai7yhwsmgvps5y"],
      "owner": null,
      "version": null,
      "epoch": 0,
      "createdAt": 1794787200000,
      "lastGseq": 17,
      "lastTime": 1794787260000
    },
    {
      "chatId": "7xkq3m2v5c6b4n7z2a3s4d5f6g",
      "kind": "group",
      "members": ["mmg42klgyqzwneiskrelxms3j4", "oln3om3moz4aai7yhwsmgvps5y", "r4xo4eaxzvnugbrpgyc475oq5i"],
      "owner": "mmg42klgyqzwneiskrelxms3j4",
      "version": 3,
      "epoch": 2,
      "createdAt": 1794787200000,
      "lastGseq": 40,
      "lastTime": 1794787290000
    }
  ]
}
```

- `kind`: `dm` или `group`.
- `members` по возрастанию. У группы это список для доставки, который ведёт сервер; он может отличаться от подписанного состояния (например, после выхода участника до следующей версии состояния). Клиент сверяет их и показывает расхождение.
- `owner`, `version`: у группы владелец и текущая версия состояния; у личного чата `null`.
- `epoch`: текущая эпоха; события чата принимаются только с ней.
- `lastGseq` и `lastTime` относятся к последнему событию участников (служебные записи не считаются), которое ещё лежит на сервере; `null`, если таких нет (чат пуст после очистки по сроку или группа только создана; такой чат остаётся в списке).

### 5.3. `POST /v1/chats/<chatId>/events`

Отправить событие. Заголовки:

| Заголовок | Значение |
| --- | --- |
| `Authorization` | `Bearer <токен>` |
| `Content-Type` | `application/octet-stream` (сервер не проверяет) |
| `Idempotency-Key` | `msgId` события, base32 16 байт, 26 символов; обязателен |
| `X-FC-Epoch` | эпоха события, десятичное u32; обязателен; у личного чата `0` |
| `X-FC-Push` | необязателен: значение `none` значит «не присылать уведомление о событии» |

Тело: зашифрованное событие, сырые байты, от 1 до 262144 байт. Сервер его не разбирает.

**Подсказка `X-FC-Push: none`.** Отправитель помечает событие, которое не стоит уведомления: клиент ставит её на `edit`, `delete` и `react` (в том числе на реакцию на чужое сообщение: уведомлений о реакциях нет, поэтому получатель не получает уведомления и о реакции на своё сообщение). Сервер такое событие хранит и доставляет как обычно, только не шлёт push (раздел 9). Любое другое значение заголовка даёт 400 `bad_request`, чтобы опечатка не превращалась в уведомление. Это подсказка отправителя: сервер её не проверяет (содержимое события он прочитать не может), и злонамеренный клиент может лишь лишить получателей уведомления о своём собственном сообщении.

Цена по метаданным: кроме чата, отправителя, времени и размера (выровненного до 256 байт) сервер узнаёт, какие события служебные (правка, удаление или реакция), а какие новые сообщения. Какое именно из трёх служебное и к какому сообщению оно относится, остаётся зашифрованным. Мы приняли эту цену: без подсказки каждая реакция и правка будила телефон «Новым сообщением», что хуже и для людей, и для батареи.

Ответ 200:

```json
{"gseq": 18, "time": 1794787261234, "duplicate": false}
```

- `gseq` и `time` выдаёт сервер; порядок и время в ленте берутся отсюда.
- Ответ приходит только после того, как событие записано на диск (`fsync`).
- Повтор с тем же `Idempotency-Key` от того же участника в тот же чат возвращает прежние `gseq` и `time` с `"duplicate": true` и ничего не записывает; тело повтора не сравнивается. Это действует и после перезапуска сервера, пока исходное событие не удалено по сроку. Клиент при обрыве связи повторяет отправку с тем же ключом.
- В группу пишут только её текущие участники; исключение участника из семьи отправку в группу не блокирует.
- После записи сервер шлёт уведомления (раздел 9; не шлёт, если пришёл `X-FC-Push: none`) и будит длинные запросы получателей.

Ошибки:

| Статус | `error` | Причина |
| --- | --- | --- |
| 400 | `bad_request` | неверный `chatId`, нет или неверный `Idempotency-Key` или `X-FC-Epoch`, `X-FC-Push` не `none`, пустое тело |
| 403 | `not_member` | чат существует, я не участник (в том числе вышел или удалён из группы) |
| 403 | `peer_removed` | личный чат: собеседник исключён из семьи или отозвал идентичность |
| 404 | `chat_not_found` | нет группы с этим `chatId`, и ни с одним участником (включая меня) он не сходится как личный |
| 409 | `epoch_mismatch` | эпоха не равна текущей эпохе чата; в ответе `"epoch": <текущая>` |
| 409 | `idempotency_conflict` | этот `Idempotency-Key` уже использован мной в другом чате |
| 413 | `too_large` | тело больше 262144 байт; `"limit": 262144` |
| 507 | `storage_full` | мало места на диске |

На 409 `epoch_mismatch` в группе клиент получает новый ключ (`GET /v1/keys`), шифрует событие заново той же `msgId` и отправляет снова. Сообщение не теряется и не дублируется.

### 5.4. `GET /v1/events?after=<gseq>&limit=<n>&wait=<сек>`

Мои записи (события всех моих чатов и адресованные мне служебные записи) с `gseq > after`, от старых к новым. Это основной канал доставки.

- `after`: последний полученный `gseq`, по умолчанию 0.
- `wait`: если подходящих записей нет, сервер держит запрос до `wait` секунд (не больше 30) и отвечает сразу, как только появится запись для меня. Пока приложение открыто, клиент держит `wait=25` и сразу повторяет запрос после ответа.

Ответ 200:

```json
{
  "events": [
    {
      "kind": "event",
      "gseq": 18,
      "time": 1794787261234,
      "chatId": "lo2a5ewrojycetbvska5utmpxe",
      "senderId": "mmg42klgyqzwneiskrelxms3j4",
      "devId": "aaaqeayeaudaocaj",
      "epoch": 0,
      "msgId": "aaaqeayeaudaocajbifqydiob4",
      "body": "<base64url тела события>"
    },
    {
      "kind": "notice",
      "gseq": 19,
      "time": 1794787262000,
      "chatId": "7xkq3m2v5c6b4n7z2a3s4d5f6g",
      "notice": {"type": "member_left", "userId": "oln3om3moz4aai7yhwsmgvps5y", "members": ["…"], "version": 3, "epoch": 2}
    }
  ],
  "cursor": 19,
  "more": false,
  "oldestGseq": 1,
  "oldestTime": 1794700000000
}
```

- `kind`: `event` (зашифрованное событие участника) или `notice` (служебная запись сервера, раздел 7). У служебной записи нет `senderId`, `devId`, `epoch`, `msgId`, `body`; вместо них `notice`. Запись с неизвестным `notice.type` клиент пропускает.
- `cursor`: значение для следующего `after`. Клиент **всегда** заменяет свой курсор на `cursor`, даже если он меньше прежнего (сервер восстановили из старой копии). Если `more: false`, `cursor` равен последнему `gseq` на сервере, в том числе записей чужих чатов: номера сквозные, поэтому в `gseq` моих записей бывают пропуски, это нормально.
- `more: true`: записей больше, чем поместилось (`limit` или около 4 МиБ тел), клиент сразу запрашивает следующую страницу с `after=cursor`.
- `oldestGseq`: самый старый `gseq`, который ещё лежит на сервере (если журнал пуст, следующий номер). Если `after + 1 < oldestGseq`, часть записей после курсора могла быть удалена по сроку хранения: клиент показывает отметку «сообщения до <дата> с сервера уже удалены» и предлагает импорт архива. Для нового устройства с `after=0` это ожидаемо.
- `oldestTime`: время (по часам сервера) самой старой записи, которая ещё лежит на сервере; `null`, если журнал пуст. Это и есть `<дата>` в отметке выше.
- `senderId` и `devId` поставил сервер по токену отправителя; `msgId` это его `Idempotency-Key`. Клиент всё равно проверяет подпись внутри тела.
- `deleted`: у события, удалённого «у всех» (5.6), `"deleted": true` и пустое `body` (`""`); заголовок (`gseq`, `time`, `senderId`, `devId`, `epoch`, `msgId`) остаётся. У остальных событий поля нет. Удалённая запись в подсчёте около 4 МиБ на ответ занимает 0 байт.
- Кому доставляется событие группы: тем, кто был её участником в момент события, то есть после служебной записи, добавившей его (`group_created` или `group_state` с ним в `added`), и до записи, убравшей его (`group_state` с ним в `removed` или `member_left` о нём). Запись о его удалении он получает, а после неё из этой группы ничего. События группы до своего вступления новый участник видит только через историю (5.5).
- Пустой ответ (`events: []`) после ожидания это норма.
- При остановке сервера ждущие запросы получают пустой ответ 200.
- Запрос, который уже ждёт со старым токеном, дорабатывает до конца ожидания, даже если токен тем временем заменён (новый вход того же устройства через `auth/device`): проверка токена идёт в начале запроса. Следующий запрос со старым токеном получит 401. Исключение участника и отзыв идентичности, наоборот, заканчивают его ждущие запросы сразу (403 `removed` или `revoked`).
- 400 `bad_request` при нечисловых `after`, `limit`, `wait`.

### 5.5. `GET /v1/chats/<chatId>/events?before=<gseq>&limit=<n>`

История одного чата назад, для прокрутки. Возвращает до `limit` (по умолчанию 200, не больше 500) последних записей чата с `gseq < before` (без `before`: самые новые), в порядке от старых к новым, в том же виде, что `/v1/events`.

- Доступна только текущим участникам чата. У группы отдаются все лежащие на сервере события участников, в том числе написанные до моего вступления (их ключ может быть мне неизвестен), и только адресованные мне служебные записи.

Ответ 200:

```json
{"events": [ … как в /v1/events … ], "cursor": 5, "more": true, "oldestGseq": 1, "oldestTime": 1794700000000}
```

- `cursor`: `gseq` самой старой записи в ответе; следующая страница: `before=cursor`. Если записей нет, `cursor` равен меньшему из `before` и следующего номера на сервере.
- `more: true`: на сервере есть ещё более старые записи этого чата.
- Личный чат (и чат с самим собой), который ещё не создан, но `chatId` которого сходится со мной и участником, отвечает пустым списком.

Ошибки: 400 `bad_request` (неверный `chatId` или параметры), 403 `not_member` (в том числе бывший участник группы), 404 `chat_not_found`.

### 5.6. `DELETE /v1/chats/<chatId>/events/<gseq>`

«Удалить у всех»: тело события на сервере затирается нулями, другим участникам приходит служебная запись `event_deleted` (раздел 7). Тело запроса пустое. Ответ 204, в том числе при повторе: удалённое событие удаляется снова с тем же ответом, вторая служебная запись не пишется.

- Удалить может отправитель события и, в группе, её текущий владелец. Запрос шлёт текущий участник чата.
- `gseq` это номер записи из `GET /v1/events` или истории, десятичное число без ведущих нулей, не меньше 1.
- Служебные записи удалить нельзя (404 `event_not_found`).
- Сервер не видит, что внутри: вложения сообщения клиент удаляет сам (`DELETE /v1/blobs/<id>`, их может удалить только загрузивший), а зашифрованное событие `delete` (`docs/PROTOCOL.md` 7.2a) клиент отправляет до этого запроса.
- После ответа запись в `GET /v1/events` и истории идёт с `"deleted": true` и пустым `body`. Повтор отправки с тем же `Idempotency-Key` по-прежнему отвечает прежним `gseq` с `duplicate: true`, нового события не появляется.
- Удаление переживает перезапуск сервера (раздел 12.3).

Ошибки:

| Статус | `error` | Причина |
| --- | --- | --- |
| 400 | `bad_request` | неверный `chatId` или `gseq` |
| 403 | `not_member` | я не участник чата |
| 403 | `not_author` | событие отправил другой участник, а я не владелец группы |
| 404 | `chat_not_found` | нет такого чата |
| 404 | `event_not_found` | в этом чате нет события участника с таким `gseq` (ещё не создано, другого чата, служебная запись); у личного чата, который ещё не создан |
| 410 | `expired` | событие уже удалено по сроку хранения (`gseq` меньше `oldestGseq`) |

## 6. Группы

Сервер не видит ни названия, ни состава из подписанного состояния, ни ключей: документ состояния и запечатанные ключи для него непрозрачные байты (их формат в `docs/PROTOCOL.md`). Сервер ведёт только данные для доставки: `chatId`, владельца, список участников, версию состояния и эпоху. Все изменения группы идут через один поток записи сервера, поэтому две версии с одним номером невозможны.

### 6.1. `POST /v1/chats`

Создать группу одним запросом: состояние версии 1, участники, запечатанный ключ каждому. Сервер пишет всё или ничего. Тело (до 1 МиБ):

```json
{
  "chatId": "7xkq3m2v5c6b4n7z2a3s4d5f6g",
  "state": "<base64url документа состояния версии 1>",
  "members": ["mmg42klgyqzwneiskrelxms3j4", "oln3om3moz4aai7yhwsmgvps5y"],
  "epoch": 0,
  "keys": [
    {"userId": "mmg42klgyqzwneiskrelxms3j4", "key": "<запечатанный ключ: непрозрачная строка>"},
    {"userId": "oln3om3moz4aai7yhwsmgvps5y", "key": "<строка>"}
  ]
}
```

- `chatId`: 16 случайных байт в base32, выбирает клиент. Занятый id (существующий чат или id личного чата любых двух участников, включая чат с собой) даёт 409 `chat_exists`.
- Создатель становится владельцем и должен быть в `members`. Каждый участник должен быть действующим участником семьи (не исключён, не отозван), иначе 400 `bad_member`. Повторы в `members` и `keys` дают 400.
- `epoch`: начальная эпоха (u32), её выбирает клиент по `docs/PROTOCOL.md`.
- `keys`: ровно один ключ на каждого участника (создателю тоже, для его других устройств), иначе 400. `key` это непрозрачная строка от 1 до 8192 байт (раздел 1.2). Ключи записываются получателям с эпохой `epoch` и версией 1 (6.5).
- Лишние поля тела дают 400.

Ответ 201: объект чата как элемент `GET /v1/chats` (`version: 1`, `owner` = я). Все участники получают служебную запись `group_created`.

Ошибки: 400 `bad_request`, 400 `bad_member`, 409 `chat_exists`, 413 `too_large`, 507 `storage_full`.

Повтор после обрыва связи: 409 `chat_exists` означает, что, скорее всего, первая попытка прошла; клиент проверяет `GET /v1/chats` и `GET /v1/chats/<id>/state/1`.

### 6.2. `PUT /v1/chats/<chatId>/state`

Смена состояния (название, участники, владелец, новая эпоха) с условием по версии. Принимается только от текущего владельца и только если сохранённая версия равна `baseVersion`; новая версия `baseVersion + 1`. Всё или ничего. Тело (до 1 МиБ):

```json
{
  "baseVersion": 3,
  "state": "<base64url документа состояния версии 4>",
  "members": ["mmg42klgyqzwneiskrelxms3j4", "r4xo4eaxzvnugbrpgyc475oq5i"],
  "owner": "mmg42klgyqzwneiskrelxms3j4",
  "epoch": 3,
  "keys": [
    {"userId": "mmg42klgyqzwneiskrelxms3j4", "key": "<строка>"},
    {"userId": "r4xo4eaxzvnugbrpgyc475oq5i", "key": "<строка>"}
  ]
}
```

- `members`: новый список для доставки целиком. Добавляемые должны быть действующими участниками семьи (400 `bad_member`); уже состоящие могут оставаться, даже если их исключили из семьи.
- `owner`: новый владелец (передача владения), должен быть в `members` и действующим участником семьи. Прежний владелец может в этом же запросе выйти из `members`.
- `epoch`: текущая эпоха или следующая (+1). Если из списка сервера кто-то убран (удалён владельцем, в том числе прежний владелец), эпоха обязана быть следующей. Иначе 400 с `"epoch": <текущая>`. Участник, вышедший сам (6.4), из списка сервера уже убран и в этом правиле не считается; его ключ владелец меняет по правилам протокола (сверка с подписанным состоянием).
- `keys`: ключи только для участников из нового `members`. При новой эпохе нужен ровно один ключ на каждого участника; при той же эпохе нужен ключ каждому добавленному, остальным по желанию (например, тем, кто его потерял). Ключи записываются с новой эпохой и новой версией.

Ответ 200: объект чата как элемент `GET /v1/chats` с новыми `version`, `epoch`, `owner`, `members`. Старым и новым участникам приходит служебная запись `group_state`.

Ошибки:

| Статус | `error` | Причина |
| --- | --- | --- |
| 400 | `bad_request` | тело, поля, эпоха, владелец не в `members`, ключи не по правилам, чат не группа |
| 400 | `bad_member` | добавляемый участник или новый владелец не из семьи |
| 403 | `not_member` | я не участник |
| 403 | `not_owner` | я не владелец |
| 404 | `chat_not_found` | нет такого чата |
| 409 | `stale_version` | версия уже не `baseVersion`; в ответе `"version": <текущая>` |
| 413 | `too_large` | тело больше 1 МиБ |
| 507 | `storage_full` | мало места на диске |

Проверки идут в таком порядке: чат, участие, владелец, версия, остальное. На 409 `stale_version` клиент читает новую версию, применяет своё изменение к ней и пробует снова. Повтор после обрыва связи тоже может получить 409 с `version = baseVersion + 1`: тогда клиент сравнивает `GET /v1/chats/<id>/state/<version>` со своим документом, чтобы понять, прошла ли его смена.

### 6.3. `GET /v1/chats/<chatId>/state/<version>`

Документ состояния указанной версии (1..текущая), сырые байты, `Content-Type: application/octet-stream`. Старые версии сервер хранит, пока существует чат. Только текущим участникам.

Ошибки: 400 `bad_request` (неверный `chatId` или `version`, чат не группа), 403 `not_member`, 404 `chat_not_found`, 404 `not_found` (нет такой версии).

### 6.4. `POST /v1/chats/<chatId>/leave`

Выйти из группы. Тело пустое. Ответ 204. Сервер сразу убирает участника из списка доставки; версия состояния и эпоха не меняются (подписанное состояние ещё содержит вышедшего, пока владелец не выпустит новую версию). Оставшимся участникам и самому вышедшему приходит служебная запись `member_left`; после неё вышедший из этой группы ничего не получает.

Клиент отправляет только этот запрос: отдельного зашифрованного события о выходе в протоколе нет. Остальные клиенты узнают о выходе из служебной записи `member_left` (раздел 7) и показывают строку «… вышел(а) из группы»; владелец затем выпускает новое состояние без вышедшего и новую эпоху.

Ошибки: 400 `bad_request` (чат не группа), 403 `not_member`, 404 `chat_not_found`, 409 `owner_cannot_leave` (владелец сначала передаёт владение сменой состояния).

### 6.5. `GET /v1/keys?after=<n>&limit=<k>`

Мои запечатанные ключи групп с номером больше `after`, по возрастанию номера. Ответ 200:

```json
{
  "keys": [
    {"n": 7, "chatId": "7xkq3m2v5c6b4n7z2a3s4d5f6g", "epoch": 3, "version": 4, "time": 1794787300000, "key": "<строка, как её прислал владелец>"}
  ],
  "cursor": 7,
  "more": false
}
```

- `n`: номер ключа у этого пользователя, растёт на единицу с 1; `cursor` это `n` последнего ключа в ответе (или `after`, если ключей нет). Клиент хранит курсор и запрашивает новые ключи при служебных записях `group_created` и `group_state` и при 409 `epoch_mismatch`.
- `epoch`, `version`: эпоха ключа и версия состояния, с которой он записан.
- Ключи хранятся, пока существует чат, в том числе после выхода или удаления из группы (для расшифровки старых событий). Отдаются только самому получателю.
- 400 `bad_request` при нечисловых `after`, `limit`.

## 7. Служебные записи сервера

Служебная запись (`kind: "notice"`) это незашифрованная запись, которую пишет сам сервер. У неё свой `gseq` в общем журнале, она лежит рядом с событиями, доставляется тем же `GET /v1/events` только своим адресатам и удаляется по сроку хранения вместе со своим днём. Отличить от события участника: `kind == "notice"` и поле `notice` вместо `body`. Подделать её участник не может: события участников всегда приходят с `kind: "event"`.

Список адресатов сервер клиентам не отдаёт. Все `userId` в списках по возрастанию.

| `notice.type` | Поля | Кому | Когда |
| --- | --- | --- | --- |
| `group_created` | `by`, `owner`, `members`, `version` (1), `epoch` | всем участникам | группа создана (6.1) |
| `group_state` | `by` (прежний владелец), `owner`, `members`, `version`, `epoch`, `added`, `removed` | участникам до и после смены | состояние сменилось (6.2). Если мой `userId` в `removed`, меня удалили из группы: это последняя запись из неё |
| `member_left` | `userId`, `members` (оставшиеся), `version`, `epoch` | оставшимся и вышедшему | участник вышел (6.4) |
| `member_removed` | `userId` | владельцу группы | участника группы исключили из семьи (10). Если исключён сам владелец, запись получают все остальные участники группы |
| `member_revoked` | `userId` | владельцу группы | участник группы отозвал идентичность (4.5). Если это владелец, запись получают остальные участники |
| `event_deleted` | `gseq`, `senderId`, `msgId` (удалённого события), `by` (кто удалил) | текущим участникам чата, удалившему тоже (для его других устройств) | событие удалено «у всех» (5.6). Подсказка: подписи у неё нет, право на удаление клиент проверяет по зашифрованному событию `delete` |

Пример:

```json
{"kind": "notice", "gseq": 51, "time": 1794787300000, "chatId": "7xkq3m2v5c6b4n7z2a3s4d5f6g",
 "notice": {"type": "group_state", "by": "mmg4…", "owner": "mmg4…", "members": ["mmg4…", "r4xo…"], "version": 4, "epoch": 3, "added": ["r4xo…"], "removed": ["oln3…"]}}
```

- Запись сообщает о факте, но не заменяет подписанное состояние: клиент по ней читает `GET /v1/chats/<id>/state/<version>`, новые ключи `GET /v1/keys` и проверяет подписи владельца.
- `member_removed` и `member_revoked` это подсказка владельцу сменить состояние и эпоху (владелец, увидевший её, удаляет участника при следующем запуске).
- Если сервер упал между фиксацией изменения группы и записью служебной записи, изменение сохранено, а записи не будет. Поэтому клиент при запуске сверяет `GET /v1/chats` (версии и эпохи) со своей базой.

## 8. Вложения

Файл режется клиентом на части до 4 МиБ открытого текста, каждая часть шифруется (`docs/PROTOCOL.md`). Сервер хранит части как непрозрачные байты в `blobs/<день>/<blobId>/<NNNN>`, где день (UTC) это день загрузки первой части. Событие `msg` со ссылкой на вложение клиент публикует только после загрузки всех частей.

- Добавлять части и удалять вложение может только загрузивший (владелец задаётся первой загруженной частью).
- Скачивать может любой действующий участник семьи, знающий `blobId` (128 случайных бит из сообщения).
- Части нумеруются 0-9999, их можно слать в любом порядке и повторять: повторно присланная часть заменяет прежнюю. Так загрузка возобновляется после обрыва: клиент спрашивает `GET /v1/blobs/<blobId>`, какие части уже есть и какого размера, и досылает недостающие (и последнюю, если её размер не тот).
- Часть пишется во временный файл и переименовывается на место только целиком; оборванная загрузка части ничего не оставляет.
- Вложение удаляется вместе со своим днём по сроку хранения (раздел 11).

### `PUT /v1/blobs/<blobId>/<part>`

Тело: байты части, от 1 до 4194560 байт. Ответ 200:

```json
{"blobId": "…", "part": 3, "size": 4194320, "total": 16777280}
```

`size` размер этой части, `total` сумма всех частей вложения после записи.

Ошибки:

| Статус | `error` | Причина |
| --- | --- | --- |
| 400 | `bad_request` | неверный `blobId` или номер части, пустое тело |
| 403 | `not_owner` | вложение загружает другой участник |
| 413 | `too_large` | часть больше 4194560 байт (`"limit": 4194560`) или вложение стало бы больше `maxBlobBytes` (`"limit": <maxBlobBytes>`); в сумму идёт новый размер заменяемой части |
| 507 | `storage_full` | свободного места меньше порога сервера плюс размер части |

Если тело пришло без `Content-Length` (chunked), предел проверяется по ходу приёма.

### `GET /v1/blobs/<blobId>/<part>`

Байты части. Заголовки: `Content-Type: application/octet-stream`, `Content-Length`, `Content-Disposition: attachment`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; sandbox`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`. Ошибки: 400 `bad_request`, 404 `blob_not_found` (нет вложения или части).

### `GET /v1/blobs/<blobId>`

Что уже загружено. Любому участнику семьи. Ответ 200:

```json
{
  "blobId": "…",
  "owner": "mmg42klgyqzwneiskrelxms3j4",
  "createdAt": 1794787200000,
  "parts": [{"part": 0, "size": 4194320}, {"part": 1, "size": 1200}],
  "total": 4195520,
  "maxBytes": 209780736
}
```

Ошибки: 400 `bad_request`, 404 `blob_not_found`.

### `DELETE /v1/blobs/<blobId>`

Удалить вложение со всеми частями. Ответ 204. Ошибки: 400, 403 `not_owner`, 404 `blob_not_found`.

## 8a. Наборы стикеров

Наборы стикеров семьи. Набор загружается файл за файлом (черновик, его видит только загрузивший), затем публикуется подписанным манифестом; опубликованный набор неизменяем, его видят и скачивают все участники семьи, удалить может только загрузивший. Формат манифеста и стикера в сообщении: `docs/PROTOCOL.md`, раздел 18.

**Стикеры не шифруются.** Набор публикуется для всех участников сервера и не имеет ключа, поэтому файлы и манифест лежат на сервере открыто: их может прочитать тот, у кого есть доступ к папке данных или к серверу. Подлинность защищена подписью загрузившего и хэшем каждого файла, а не шифрованием. Сообщение со стикером (какой стикер, кому, когда) шифруется, как любое сообщение.

**Срок хранения на наборы не действует.** Наборы лежат в `packs/` и не удаляются по сроку хранения переписки (раздел 11): они нужны, пока ими пользуются, и удаляются только загрузившим. Неопубликованный черновик сервер удаляет через сутки. Исключение или отзыв загрузившего набор не удаляет.

Пределы: файл `.webp` до 524288 байт, `.tgs` до 131072 байт, в наборе 1-200 стикеров и до 52428800 байт всего, не больше 200 наборов на сервере (вместе с черновиками), манифест до 65536 байт. Пределы набора есть в `/v1/hello` (`maxPackStickers`, `maxPackBytes`).

### `PUT /v1/packs/<packId>/files/<hash>`

Один файл черновика, тело: сырые байты. `packId`: base32 16 байт (26 символов), выбирает клиент. `hash`: base32 первых 20 байт SHA-256 файла (32 символа). Сервер проверяет: тип по первым байтам (WebP `RIFF....WEBP` или gzip `1F 8B` для `.tgs`; SVG, HTML, PNG и прочее отвергаются), предел своего типа, что `hash` равен хэшу байт. Первый файл создаёт черновик и делает вызвавшего его владельцем. Повтор того же файла отвечает 200. Ответ:

```json
{"packId": "…", "file": "<hash>", "type": "webp", "size": 31544}
```

Ошибки: 400 `bad_request` (идентификаторы), 400 `bad_sticker` (не WebP и не gzip), 400 `hash_mismatch`, 403 `not_owner` (черновик другого участника), 409 `pack_published`, 413 `too_large` (файл, больше 200 файлов или больше предела набора), 507 `too_many_packs`, 507 `storage_full`.

### `PUT /v1/packs/<packId>`

Публикация. Тело: конверт манифеста `{"payload", "sig"}` (вид `sticker-pack`, подпись ключом идентичности загрузившего). Сервер проверяет форму и пределы манифеста, `serverId` (свой), что `packId` совпадает с адресом, что `author` это вызвавший, подпись, и что каждый перечисленный файл загружен с тем же типом и размером. Файлы черновика, которых нет в манифесте, удаляются. Повтор той же публикации отвечает 200, другой манифест для опубликованного набора 409. Ответ: элемент списка (ниже).

Ошибки: 400 `bad_manifest`, 400 `bad_signature`, 403 `not_author`, 403 `not_owner`, 404 `pack_not_found`, 409 `missing_file` или `file_mismatch` (с полем `"file"`), 409 `pack_published`.

### `GET /v1/packs`

Опубликованные наборы, старые первыми:

```json
{"packs": [{"packId": "…", "owner": "<userId>", "manifest": {"payload": "…", "sig": "…"}, "publishedAt": 1794787261234, "bytes": 182211}]}
```

Манифест отдаётся ровно как был подписан. Клиент проверяет его сам (подпись по `identity` владельца из `GET /v1/users`, `serverId`, `packId`) и не доверяет списку сервера.

### `GET /v1/packs/<packId>`

Один опубликованный набор (тот же объект). 404 `pack_not_found` для черновика или удалённого.

### `GET /v1/packs/<packId>/files/<hash>`

Файл опубликованного набора: `application/octet-stream`, `Content-Disposition: attachment`, `Cache-Control: private, max-age=31536000, immutable`, `Content-Security-Policy: … sandbox`. Клиент сверяет хэш и размер с манифестом до показа, `.tgs` распаковывает с пределом и очищает (`docs/PROTOCOL.md` 18.4). 404 `file_not_found`.

### `DELETE /v1/packs/<packId>`

Удалить набор (опубликованный или черновик) у всех. Только загрузивший: иначе 403 `not_owner`; 404 `pack_not_found`. Ответ 204. В отправленных сообщениях стикер становится заглушкой с его эмодзи.

## 9. Уведомления

### `PUT /v1/me/push`

Подписка Web Push для текущего устройства. Тело как `PushSubscription.toJSON()`:

```json
{"endpoint": "https://fcm.googleapis.com/fcm/send/…", "keys": {"p256dh": "<base64url 65 байт>", "auth": "<base64url 16 байт>"}}
```

`endpoint` только `https://` (до 2048 символов), `p256dh` несжатая точка P-256 (65 байт, первый 0x04), `auth` 16 байт; лишние поля (`expirationTime`) пропускаются. Новая подписка заменяет прежнюю. Ответ 204 без тела.

Ошибки: 400 `bad_request`, 409 `push_disabled` (на сервере `push = false`).

### `DELETE /v1/me/push`

Удалить подписку текущего устройства. Ответ 204, в том числе если подписки не было.

### Что приходит

На каждое новое событие участника (не на повтор, не на служебную запись и не на событие с `X-FC-Push: none`, раздел 5.3) сервер шлёт уведомление на все устройства с подпиской всех текущих участников чата, **включая другие устройства отправителя**; не получает его только устройство, отправившее событие. Исключённым и отозвавшим идентичность не идёт. Полезная нагрузка, зашифрованная по RFC 8291 (`aes128gcm`), это JSON

```json
{"chatId": "lo2a5ewrojycetbvska5utmpxe", "gseq": 18}
```

Текста и имён в уведомлении нет. Заголовки запроса к push-сервису: `TTL: 300`, `Urgency: high`. Service worker показывает «Новое сообщение» и имя чата из локальной базы; уведомление о собственном сообщении с другого устройства клиент может не показывать, сравнив отправителя после синхронизации. Подписку, на которую push-сервис ответил 404 или 410, сервер удаляет (`GET /v1/me` покажет `push: false`); клиенту стоит подписаться заново при следующем запуске.

## 10. Администрирование

Все запросы требуют токен администратора; иначе 403 `not_admin`.

### `POST /v1/admin/invites`

Тело пустое. Ответ 201:

```json
{"id": "<64 hex>", "code": "<26 символов base32>", "createdAt": 1794787200000, "expiresAt": 1795392000000}
```

`code` показывается только здесь, один раз: на сервере хранится лишь его SHA-256 (`id` это этот хэш в hex) и кто выпустил приглашение. Срок 7 суток.

### `GET /v1/admin/invites`

Ответ 200, по времени создания:

```json
{
  "invites": [
    {"id": "…", "createdAt": 1794787200000, "expiresAt": 1795392000000, "createdBy": "<userId>", "usedAt": null, "usedBy": null}
  ]
}
```

Использованные приглашения видны с `usedAt` и `usedBy` до конца срока. Просроченные удаляются ежечасной очисткой.

### `DELETE /v1/admin/invites/<id>`

Отозвать приглашение. 204; 404 `not_found`, если такого нет; 400 при неверном `id` (64 строчных hex-символа).

### `GET /v1/admin/users`

Ответ 200, по `userId`:

```json
{
  "users": [
    {
      "userId": "…",
      "name": "Мама",
      "admin": true,
      "removed": false,
      "removedAt": null,
      "revoked": false,
      "revokedAt": null,
      "devices": [{"devId": "…", "createdAt": 1794787200000, "push": true}]
    }
  ]
}
```

`name` взят из подписанного профиля (сервер его видит в открытом виде). `revokedAt`: время по часам сервера, когда принят отзыв.

### `DELETE /v1/admin/users/<userId>`

Исключить участника. Ответ 204 (повтор тоже 204). Сразу после этого:

- все токены участника получают 403 `removed`, его ждущие `GET /v1/events` заканчиваются 403;
- `auth/device` для него отвечает 403;
- его события не принимаются, ему ничего не доставляется и не уведомляется;
- отправка в личный чат с ним отвечает 403 `peer_removed`;
- если он был администратором, перестаёт им быть;
- владельцы групп, где он состоит, получают служебную запись `member_removed` (раздел 7). Из списков групп сервер его сам не убирает.

Его прежние события остаются у собеседников и на сервере до конца срока хранения; в `GET /v1/users` он остаётся с `removed: true`.

Ошибки: 400 (неверный `userId`), 404 `unknown_user`, 409 `cannot_remove_self`.

### `GET /v1/admin/stats`

Ответ 200:

```json
{
  "version": "1.0.0",
  "commit": "3208eeb2c67a",
  "dataBytes": 1234567,
  "freeBytes": 9876543210,
  "totalBytes": 32000000000,
  "events": 4210,
  "oldestGseq": 120,
  "lastGseq": 4329,
  "users": 5,
  "removedUsers": 0,
  "chats": 7,
  "groups": 2,
  "retentionDays": 90,
  "push": true
}
```

`users`: число текущих участников, исключённые в него не входят (они считаются в `removedUsers`). `events`: записи журнала, служебные тоже. `chats`: все чаты, группы тоже; `groups`: из них групп. `dataBytes`: сумма размеров файлов папки данных. `freeBytes`, `totalBytes`: место файловой системы, где лежит папка (доступное непривилегированному процессу); `null`, если система не сообщила их (на Linux, macOS и Windows сервер их узнаёт). Когда свободного меньше `min_free_mb` из настроек (по умолчанию 100 МБ), отправка событий, создание и смена групп, вступление, загрузка аватара и частей вложений отвечают 507.

## 10a. Проверка сервера

Длинный запрос и пробное уведомление. Доступ:
`Authorization: Bearer <значение>`, где значение либо действующий код администратора (страница `/server/` до входа
первого администратора), либо токен устройства администратора (раздел «Проверка сервера» в приложении). Порядок:

1. Нет значения: проверяется ограничение частоты (раздел 1.5), ответ 401 `unauthorized`; неудачей это не считается.
2. Значение оказалось токеном устройства: решает роль. Администратор проходит; отозванная идентичность 403
   `revoked`; исключённый 403 `removed`; не администратор 403 `not_admin`. Ограничение частоты не трогается: токен
   не подобрать, а неверные коды родственников за тем же NAT не должны запирать администратора.
3. Иначе ограничение частоты (429 `rate_limited` с `Retry-After`), затем сравнение с кодом администратора. Не
   совпало: неудача засчитывается (счётчик общий с вступлением, это тот же секрет) и ответ 401: `admin_code_inactive`,
   если кода уже нет (первый администратор вошёл), иначе `unauthorized`.

Значение (код или токен) в журнал не пишется.

```sh
curl -H "Authorization: Bearer $CODE" https://chat.example.org/v1/check/wait?seconds=1
```

### `GET /v1/check/wait?seconds=<n>`

Отвечает через `n` секунд (по умолчанию 25, не больше 60), до этого ничего не шлёт. Проверяет, что прокси не обрывает
долгие запросы. Ответ 200: `{"seconds": 25, "startedAt": <мс>, "finishedAt": <мс>}`. При остановке сервера во время
ожидания 503 `shutting_down`.

### `POST /v1/check/push`

Тело: `{"delaySeconds": 0, "from": "app"}`; `delaySeconds` от 0 до 300, `from` необязательно: `"page"` (по
умолчанию) или `"app"`, другое значение 400. С токеном устройства уведомление идёт на подписку этого устройства из
`PUT /v1/me/push`; поле `subscription` в теле тогда не принимается (400), нет сохранённой подписки 409
`no_subscription`. С кодом администратора подписка передаётся в теле: `"subscription": <PushSubscription.toJSON()>`.

- `delaySeconds: 0`: ответ 200 `{"sent": true, "outcome": {"status": 201, "service": "<хост push-сервиса>"}}`.
- Иначе 202 `{"sent": false, "scheduled": true, "sendAt": <мс>}`. Одновременно ждут не больше трёх отложенных
  пробных уведомлений на сервер, четвёртое 429 `too_many_pending`.
- Полезная нагрузка: `{"kind": "check-test", "delay": <с>, "sentAt": <мс>, "from": "app"|"page"}`. По `kind` service worker узнаёт пробное уведомление.

### `GET /v1/check/push`

Итог последнего пробного уведомления этого устройства (или кода администратора): `{"last": {"at": <мс>, "result":
"sent"}}` либо `{"last": null}`. `result`: `sent` или причина неудачи (`gone`, `unauthorized`, `rejected`,
`network`). Сервер держит в памяти не больше 64 таких записей, только время и итог.

### Ошибки проверки

| Код | HTTP | Когда |
| --- | --- | --- |

## 11. Срок хранения

- Сервер хранит события и служебные записи не дольше `retentionDays` (7-90, по умолчанию 90). Раз в час (и при запуске) удаляются целые дни журнала, папки вложений этих дней (`blobs/<день>/`, день загрузки первой части) и просроченные приглашения.
- День удаляется, когда весь он (по UTC) старше срока относительно точки отсчёта: меньшее из «сейчас» и «время самого нового события плюс 7 дней». Поэтому часы сервера, убежавшие вперёд, не стирают всё, а отставшие только откладывают очистку.
- Не удаляются: участники, профили, аватары, записи чатов, состояния групп всех версий, запечатанные ключи.
- Клиент узнаёт об удалённом по `oldestGseq` и `oldestTime` (раздел 5.4). Вложение, удалённое по сроку, отвечает 404 `blob_not_found`.

## 12. Безопасность и HTTPS

### 12.1. Заголовки

На каждом ответе (и клиента, и API, в том числе на ошибках и 404):

- `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- Встроенный клиент (всё вне `/v1/`): `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; media-src blob:; font-src 'self'; connect-src 'self' https: http://localhost:* http://127.0.0.1:*; worker-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. Это политика из `apps/web/vite.config.ts` (её же сборка кладёт в `<meta>`) плюс `frame-ancestors`, который в `<meta>` не работает; совпадение проверяет тест сервера.
- Кэш клиента: файлы `assets/` (имена с хэшем) `Cache-Control: public, max-age=31536000, immutable`; `sw.js` и другие файлы, оканчивающиеся на `sw.js`, `no-store`; остальное `no-cache` с `ETag`.
- API (`/v1/...`): `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; sandbox`, `Cache-Control: no-store` (кроме аватаров, раздел 4.4). Части вложений идут как `application/octet-stream` с `Content-Disposition: attachment`, поэтому браузер никогда не покажет их как страницу.

### 12.2. HTTPS со своими файлами сертификата

```bash
fcd --data /path/to/data --tls-cert /path/fullchain.pem --tls-key /path/privkey.pem
```

- Оба флага обязательны вместе (один без другого: ошибка запуска, код 2). Сертификат: цепочка в PEM (сначала сертификат сервера), ключ: PKCS#8, PKCS#1 (RSA) или SEC1 (EC) в PEM. Неверные файлы: сообщение в журнале и код выхода 1.
- С флагами сервер слушает на том же `--port` только HTTPS (TLS 1.2 и 1.3, rustls, без OpenSSL); простого HTTP на этом порту нет. Без флагов обычный HTTP.
- Сертификат читается при запуске; после замены файлов сервер нужно перезапустить.

### 12.3. Папка данных

Версия формата папки данных записана в `formatVersion` в `server.json` и сейчас равна 2. Папку более новой версии сервер не открывает («создана более новой версией fcd»).

Удаление «у всех» (5.6) хранится так:

- Запись журнала сохраняет рамку: та же длина и тот же заголовок, тело заменено нулями той же длины, crc32 пересчитан по новым байтам. Смещения следующих записей не сдвигаются, чтение и проверка CRC те же, что для любой записи. Настоящее тело события начинается с `FC1`, поэтому тело из одних нулей тоже означает удалённую запись.
- Файл `log/<ГГГГ-ММ-ДД>.del` рядом с файлом дня перечисляет удалённые записи этого дня, по 24 байта на запись: `gseq u64 | смещение u64 | размер u32 | crc32 u32` (CRC по 20 байтам перед ним). Запись в `.del` дописывается и сбрасывается на диск (`fsync`) до того, как трогается файл дня; затем тело затирается на месте и тоже сбрасывается на диск. Всё это идёт через тот же единственный поток записи, что и дозапись событий.
- При запуске сервер заново применяет каждую запись `.del` (проверив поле длины и `gseq` в заголовке записи). Так затирание, прерванное остановкой (половина тела в нулях, старый CRC), доделывается, а не принимается за оборванную запись. Оборванный хвост `.del` отбрасывается.
- Очистка по сроку удаляет `<день>.del` вместе с `<день>.seg`.

### 12.4. «Поделиться» без service worker

Установленное приложение принимает «Поделиться» (Web Share Target, `POST <адрес приложения>/share-target`, multipart). Обычно этот запрос перехватывает service worker приложения и до сервера он не доходит. Если запрос всё же дошёл (service worker ещё не установлен), сервер отвечает `303` с `Location: ./?share=unavailable` и ничего не сохраняет: приложение откроется и объяснит, что поделиться пока не вышло.

### 12.5. Папка данных: наборы стикеров

Наборы стикеров (раздел 8a) лежат в папке `packs/`:

```
packs/<packId>/
  meta.json            # {"owner", "createdAt", "publishedAt"?}: загрузивший и время
  pack.json            # конверт манифеста ровно как получен (только у опубликованного)
  <hash32>.webp        # файлы: имя это хэш содержимого
  <hash32>.tgs
```

Файлы пишутся через `tmp/` и переименовываются. Папка без читаемого `meta.json` при запуске пропускается. Очистка по сроку `packs/` не трогает; черновики старше суток удаляет ежечасное обслуживание.

## 13. Что клиенту важно помнить

1. Курсор один на сервер: последний `cursor` из `GET /v1/events`. Хранить его надо после сохранения записей в локальной базе.
2. Одно и то же событие может прийти дважды (повтор после обрыва, история и лента). Клиент отбрасывает повторы по (`senderId`, `msgId`) или по `gseq`; служебные записи по `gseq`.
3. Отправка: событие в локальную очередь, затем `POST` с `Idempotency-Key = msgId`; при обрыве или 5xx повторять с тем же ключом. 409 `epoch_mismatch` в личном чате означает ошибку клиента (эпоха всегда 0); в группе: взять новый ключ из `GET /v1/keys`, зашифровать заново, отправить с тем же `msgId`.
4. 401 на любом запросе: войти заново через `auth/challenge` + `auth/device` с тем же `devId`, затем повторить запрос. 403 `removed`: показать экран «Вас отключили от семьи», запросы прекратить. 403 `revoked`: эта идентичность отозвана, с ней больше ничего не сделать.
5. Ответы сервера не содержат имён и текста: имена берутся из подписанных профилей `GET /v1/users`, текст из расшифрованного тела, название и состав группы из подписанного состояния.
6. Служебная запись группы это повод перечитать состояние (`GET /v1/chats/<id>/state/<version>`) и ключи (`GET /v1/keys?after=<курсор ключей>`), а не источник истины: список участников сервера клиент сверяет с подписанным состоянием и показывает расхождение.
7. При запуске клиент сверяет `GET /v1/chats` со своей базой: так видны изменения, служебная запись о которых могла не записаться или уже удалена по сроку.
8. Вложение: сначала все части, потом событие со ссылкой. После обрыва `GET /v1/blobs/<blobId>` показывает, что уже лежит на сервере.
9. Аватар: `PUT /v1/me/avatar`, затем профиль с полученным объектом в `avatar`. Чужой аватар скачивается с токеном и проверяется по SHA-256.
10. Код администратора печатается в журнал сервера один раз, при создании папки данных.
11. «Удалить у всех»: сначала зашифрованное событие `delete` (`docs/PROTOCOL.md` 7.2a), затем `DELETE /v1/chats/<id>/events/<gseq>` и `DELETE /v1/blobs/<id>` своих вложений. Обнулённая запись и `event_deleted` подписи не имеют: локальную копию у получателя убирает только подписанное событие `delete` от автора или владельца группы.
12. Несколько семей: у каждого сервера свой токен, свой курсор и свой ключ VAPID. Данные одной семьи (токены, события, ключи) никогда не отправляются на сервер другой. Подписка Web Push в браузере одна и привязана к ключу VAPID одного сервера, поэтому уведомления приходят от одной семьи на устройстве; остальные синхронизируются, пока приложение открыто.
13. Стикеры: список наборов брать из `GET /v1/packs` и проверять каждый манифест самому; файл показывать только после сверки хэша и размера с манифестом.
