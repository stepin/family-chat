# API сервера `fcd` (этап M1)

Документ описывает HTTP API сервера `fcd` версии 0.1 (протокол `1`) так, чтобы по нему одному можно было написать клиент. Форматы шифрования событий описаны в `docs/PROTOCOL.md`: для сервера тело события непрозрачно.

В M1 есть: вступление по приглашению или коду администратора, устройства, участники и профили, личные чаты, события с длинным запросом, подписка на уведомления, администрирование. Групп, вложений, удаления сообщений, аватаров, `GET /keys` и состояния чатов в M1 нет; запрос к ним вернёт 404 `not_found`.

## 1. Общие правила

### 1.1. Адрес, формат, CORS

- Все запросы идут по адресу `/v1/...` того же сервера, который отдаёт клиент. Порт по умолчанию 8787, HTTPS обычно даёт обратный прокси.
- Тела запросов и ответов JSON в UTF-8 (`Content-Type: application/json`), кроме тела `POST /v1/chats/<chatId>/events`: там сырые байты (`application/octet-stream`).
- Каждый ответ API несёт `Cache-Control: no-store` и заголовки CORS: `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS`, `Access-Control-Allow-Headers: Authorization, Content-Type, Idempotency-Key, X-FC-Epoch`, `Access-Control-Expose-Headers: Retry-After`, `Access-Control-Max-Age: 86400`. Запрос `OPTIONS` на любой путь `/v1/...` отвечает 204. Cookie сервер не ставит и не читает.
- Время везде в миллисекундах от 1970-01-01 UTC (целое число) и всегда по часам сервера.

### 1.2. Кодировки и идентификаторы

| Что | Формат |
|---|---|
| двоичные значения в JSON (ключи, подписи, тела событий, `nonce`, токен) | base64url **без** `=` (RFC 4648, раздел 5) |
| base32 | алфавит RFC 4648 `a-z2-7`, **строчные** буквы, без `=` |
| `userId` | base32 первых 16 байт SHA-256(`signPub`), 26 символов |
| `devId` | base32 10 случайных байт, 16 символов; создаёт клиент |
| `msgId` (он же `Idempotency-Key`) | base32 16 случайных байт, 26 символов; создаёт клиент |
| `chatId` | base32 16 байт, 26 символов (раздел 4) |
| `serverId` | непрозрачная строка из `/v1/hello` (сейчас base64url 16 байт, 22 символа); клиент сравнивает и подставляет её дословно |
| токен устройства | base64url 32 случайных байт, 43 символа |
| код приглашения | base32 16 случайных байт, 26 символов |
| `gseq` | целое ≥ 1, сквозной номер события на сервере, растёт на единицу |
| `epoch` | u32, у личного чата всегда 0 |

Декодеры сервера строгие: base32 только строчными, base64url без `=`, длина ровно ожидаемая, неиспользуемые младшие биты последнего символа нулевые. Идентификатор в другом виде (заглавные буквы, `=`, лишний символ) сервер отвергает с 400. Поэтому идентификаторы можно сравнивать как строки.

### 1.3. Вход

Все запросы, кроме `GET /v1/hello`, `POST /v1/join`, `POST /v1/auth/challenge`, `POST /v1/auth/device`, требуют заголовок

```
Authorization: Bearer <токен устройства>
```

Токен выдаётся один раз (ответ `join` или `auth/device`), сервер хранит только его SHA-256. Токен бессрочный; он перестаёт действовать, когда устройство входит заново с тем же `devId` или когда участника исключают.

Ответы на ошибку входа:

- 401 `unauthorized`: заголовка нет, токен неизвестен или заменён. В ответе `WWW-Authenticate: Bearer`. Клиент входит заново подписью (`auth/challenge` + `auth/device`, раздел 3.3).
- 403 `removed`: участник исключён из семьи. Заново войти нельзя; локальная история остаётся.

### 1.4. Ошибки

Тело любой ошибки:

```json
{"error": "<код>", "message": "<текст для разработчика, по-английски>"}
```

Иногда добавляются поля (например `epoch`, `limit`, `rev`); они указаны у конкретных запросов. Текст `message` не для показа пользователю, клиент различает ошибки по `error` и статусу.

| Статус | Коды `error` | Когда |
|---|---|---|
| 400 | `bad_request` | неверный JSON, поле, идентификатор, заголовок; повреждённый конверт |
| 401 | `unauthorized`, `bad_signature`, `bad_nonce` | нет или неверный токен; неверная подпись; неизвестный, использованный или просроченный `nonce` |
| 403 | `removed`, `not_member`, `not_admin`, `peer_removed`, `invalid_invite`, `invalid_code` | исключён; не участник чата; не администратор; собеседник исключён; неизвестное приглашение; неверный или уже использованный код администратора |
| 404 | `not_found`, `chat_not_found`, `unknown_user` | нет такого пути или приглашения; нет такого чата; нет такого участника |
| 405 | `method_not_allowed` | путь есть, метода нет |
| 409 | `already_member`, `stale_rev`, `epoch_mismatch`, `idempotency_conflict`, `push_disabled`, `cannot_remove_self` | см. запросы |
| 410 | `invite_used`, `invite_expired` | приглашение уже использовано или просрочено |
| 413 | `too_large` | тело больше предела; в ответе `"limit": <байт>` |
| 429 | `rate_limited` | слишком много неверных кодов или подписей с адреса; заголовок `Retry-After: <секунд>` |
| 500 | `internal` | ошибка сервера (подробности в журнале сервера) |
| 507 | `storage_full` | на диске сервера мало места |

### 1.5. Ограничение частоты

Неверный код приглашения, неверный код администратора, неверная подпись (`bad_signature`) и неверный `nonce` (`bad_nonce`) засчитываются адресу клиента. После 10 таких ошибок за 60 секунд все запросы `POST /v1/join` и `POST /v1/auth/device` с этого адреса получают 429 `rate_limited` (даже с верным кодом), пока самая старая ошибка не выйдет из окна. `Retry-After` говорит, через сколько секунд.

Адрес клиента это адрес TCP-соединения. Если в настройках сервера `trust_forwarded_for = true` (только за обратным прокси), берётся последний (самый правый) адрес из `X-Forwarded-For`.

### 1.6. Подписанные конверты

Конверт это JSON-объект

```json
{"payload": "<base64url>", "sig": "<base64url>"}
```

- `payload`: base64url точных байтов UTF-8 JSON-документа. Сервер разбирает и проверяет именно эти байты, ничего не переупорядочивает и хранит конверт как есть. Декодированный `payload` не длиннее 8192 байт.
- `sig`: подпись Ed25519 (64 байта) над байтами `utf8("fc/v1/" + kind + "\n")`, за которыми сразу идут байты `payload`. `kind` один из `identity`, `profile`, `auth`. Проверка строгая (`verify_strict`).
- Лишние поля в `payload` сервер пропускает.

| `kind` | `payload` | Чем проверяется подпись | Что ещё проверяет сервер |
|---|---|---|---|
| `identity` | `{"v":1,"userId":"…","signPub":"…","boxPub":"…","created":<ms>}` | `signPub` из самого `payload` | `v == 1`; `signPub` и `boxPub` ровно 32 байта (Ed25519 и X25519, сырые); `userId` равен base32(SHA-256(signPub)[0..16]); `created` целое |
| `profile` | `{"v":1,"userId":"…","name":"…","avatar":null,"rev":<int>,"updated":<ms>}` | сохранённый `signPub` участника | `v == 1`; `userId` свой; `name` от 1 до 64 символов (Unicode), не из одних пробелов (U+FEFF тоже считается пробелом), без управляющих символов C0, DEL, C1 и символов управления направлением текста (U+061C, U+200E, U+200F, U+202A-U+202E, U+2066-U+2069), без непарных суррогатов (как в `packages/protocol`, `docs/PROTOCOL.md` 4.3); `avatar` это `null` или строка до 128 байт (в M1 всегда `null`); `rev` целое ≥ 0 и больше сохранённого; `updated` целое |
| `auth` | `{"v":1,"userId":"…","serverId":"…","nonce":"…","devId":"…"}` | сохранённый `signPub` участника | `serverId` равен серверному; `nonce` выдан этим сервером, не использован и не старше 2 минут; `devId` в формате раздела 1.2 |

Повреждённый конверт (не base64url, не JSON, не те поля) даёт 400 `bad_request`; неверная подпись даёт 401 `bad_signature`.

### 1.7. Пределы

| Что | Предел |
|---|---|
| тело события | от 1 до 262144 байт (256 КиБ) |
| тело JSON-запроса | 65536 байт |
| `limit` в `GET /v1/events` | 1-500, по умолчанию 500 (больше 500 молча уменьшается до 500) |
| `limit` в `GET /v1/chats/<id>/events` | 1-500, по умолчанию 200 |
| `wait` в `GET /v1/events` | 0-30 секунд, по умолчанию 0 (больше 30 молча уменьшается до 30) |
| сумма тел событий в одном ответе | около 4 МиБ (до кодирования base64): ответ может содержать меньше `limit` событий, тогда `more: true`; одно событие отдаётся всегда |
| срок приглашения | 7 суток |
| срок `nonce` | 2 минуты, одно использование |
| имя в профиле | 64 символа |

## 2. Сервер

### `GET /v1/hello`

Без входа. Ответ 200:

```json
{
  "protocol": 1,
  "server": "fcd",
  "version": "0.1.0",
  "serverId": "q8Jb3kVf0w2Xy7HnT1sZ9A",
  "familyName": "Семья",
  "retentionDays": 90,
  "maxFileMb": 200,
  "push": true,
  "vapidPublicKey": "BOr…",
  "time": 1794787200000,
  "maxEventBytes": 262144,
  "adminCodeActive": false,
  "m0": false
}
```

- `vapidPublicKey`: открытый ключ VAPID (несжатая точка P-256, 65 байт, base64url) для `PushManager.subscribe({applicationServerKey})`; `null`, если `push` выключен.
- `adminCodeActive`: `true`, пока код администратора ещё не использован (на сервере нет администратора). Клиент по нему выбирает экран: «введите код администратора» или «нужно приглашение».
- `time`: часы сервера; клиент может показать предупреждение о сильном расхождении, но порядок от часов клиента не зависит.
- `m0`: включены ли проверочные точки M0 (`--m0`); для чата не нужно.

## 3. Вступление и устройства

### `POST /v1/join`

Вступление в семью: по одноразовому приглашению или по коду администратора (первый вход). Без входа. Тело:

```json
{
  "invite": "<код приглашения>",
  "identity": {"payload": "…", "sig": "…"},
  "profile": {"payload": "…", "sig": "…"},
  "devId": "aaaqeayeaudaocaj"
}
```

Вместо `invite` для первого администратора передаётся `"adminCode": "<код из журнала сервера>"`. Ровно одно из двух полей, иначе 400.

- Код приглашения сервер принимает без учёта регистра и пробелов по краям. Код администратора тоже без учёта регистра, дефисов и пробелов; буквы `O`, `I`, `L` читаются как `0`, `1`, `1`.
- `identity` это конверт `identity`, `profile` это конверт `profile` того же `userId`, подписанный тем же ключом.
- Кто вошёл по коду администратора, становится администратором; код после этого перестаёт действовать (`adminCodeActive` становится `false`). Новый код выдаёт команда `fcd reset-admin-code --data <DIR>` при остановленном сервере, и следующий вошедший по нему тоже становится администратором.
- Приглашение после успешного входа помечается использованным.
- Если пользователь с этим `userId` был исключён, вступление по новому приглашению возвращает его в семью; прежние устройства остаются недействительными.

Ответ 200:

```json
{"token": "<43 символа base64url>", "userId": "mmg42klgyqzwneiskrelxms3j4", "devId": "aaaqeayeaudaocaj", "admin": true}
```

Ошибки:

| Статус | `error` | Причина |
|---|---|---|
| 400 | `bad_request` | тело, `devId`, конверты не по формату; нет или оба поля кода |
| 401 | `bad_signature` | подпись `identity` или `profile` неверна |
| 403 | `invalid_invite` | приглашение неизвестно или отозвано (после очистки и просроченное) |
| 403 | `invalid_code` | код администратора неверен или уже использован |
| 409 | `already_member` | этот `userId` уже в семье: нужен `auth/device` |
| 410 | `invite_used` | приглашение уже использовано |
| 410 | `invite_expired` | срок приглашения истёк |
| 413 | `too_large` | тело больше 64 КиБ |
| 429 | `rate_limited` | раздел 1.5 |
| 507 | `storage_full` | мало места на диске |

Сначала проверяются формат и подписи, затем код; код расходуется только если всё остальное верно. Ошибки 401, 403 и 410 этого запроса засчитываются в ограничение частоты.

Ссылка-приглашение: `https://<адрес сервера>/#invite=<код>`. Сервер её не строит и не видит фрагмент; клиент собирает ссылку из кода (ответ `POST /v1/admin/invites`) и своего адреса и после чтения убирает фрагмент из адресной строки.

### `POST /v1/auth/challenge`

Без входа, тело пустое. Ответ 200:

```json
{"nonce": "<base64url 32 байт, 43 символа>", "expiresAt": 1794787320000}
```

`nonce` действует 2 минуты и один раз. Сервер держит не больше 1000 невыданных вызовов; самые старые вытесняются.

### `POST /v1/auth/device`

Новое устройство существующего участника или вход заново после 401 (восстановление по фразе, потерянный токен). Без входа. Тело это конверт `auth`:

```json
{"payload": "<base64url от {\"v\":1,\"userId\":\"…\",\"serverId\":\"…\",\"nonce\":\"…\",\"devId\":\"…\"}>", "sig": "…"}
```

`nonce` копируется из ответа `auth/challenge` дословно, `serverId` из `/v1/hello`.

Ответ 200, как у `join`:

```json
{"token": "…", "userId": "…", "devId": "…", "admin": false}
```

- Если у участника уже есть устройство с этим `devId`, оно заменяется: старый токен перестаёт действовать, подписка на уведомления этого устройства удаляется.
- `nonce` расходуется при любой попытке, даже неудачной.

Ошибки:

| Статус | `error` | Причина |
|---|---|---|
| 400 | `bad_request` | конверт не по формату; `serverId` чужой |
| 401 | `bad_nonce` | `nonce` неизвестен, использован или просрочен |
| 401 | `bad_signature` | подпись неверна |
| 403 | `removed` | участник исключён |
| 404 | `unknown_user` | такого участника на сервере нет: нужно приглашение |
| 429 | `rate_limited` | раздел 1.5 |

## 4. Участники и профиль

### `GET /v1/users`

Все участники семьи, включая исключённых (их подписи нужны для старых сообщений). Отсортированы по `userId`. Ответ 200:

```json
{
  "users": [
    {
      "userId": "mmg42klgyqzwneiskrelxms3j4",
      "identity": {"payload": "…", "sig": "…"},
      "profile": {"payload": "…", "sig": "…"},
      "admin": true,
      "removed": false
    }
  ]
}
```

`identity` и `profile` это конверты в точности как их прислал владелец. `profile` может быть `null` только у данных, повреждённых на диске. Клиент сам проверяет подписи (`docs/PROTOCOL.md`).

### `GET /v1/me`

Свой участник и текущее устройство. Ответ 200: те же поля, что у элемента `users`, плюс

```json
{"devId": "aaaqeayeaudaocaj", "push": false}
```

`push`: есть ли у этого устройства подписка на уведомления.

### `PUT /v1/me/profile`

Тело это конверт `profile` (раздел 1.6). `rev` должен быть больше сохранённого. Ответ 200:

```json
{"profile": {"payload": "…", "sig": "…"}}
```

Ошибки: 400 `bad_request` (формат, чужой `userId`, имя длиннее 64 символов, пустое или с запрещёнными символами, раздел 1.6), 401 `bad_signature`, 409 `stale_rev` (в ответе `"rev": <сохранённый>`).

## 5. Личные чаты и события

### 5.1. Идентификатор личного чата

```
lo, hi = два userId, упорядоченные как строки (побайтно, по возрастанию)
chatId = base32( SHA-256( utf8("fc/v1/dm\n" + serverId + "\n" + lo + "\n" + hi) )[0..16] )
```

Строка хэшируется целиком, `\n` это байт 0x0A, префиксов длины нет. Пример (векторы и в `docs/vectors/dm.json`):

| Что | Значение |
|---|---|
| `signPub` A | байты 0x00..0x1f: `AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8` |
| `userId` A | `mmg42klgyqzwneiskrelxms3j4` |
| `signPub` B | байты 0x20..0x3f: `ICEiIyQlJicoKSorLC0uLzAxMjM0NTY3ODk6Ozw9Pj8` |
| `userId` B | `oln3om3moz4aai7yhwsmgvps5y` |
| `serverId` | `c2VydmVyLWlkLWV4YW1wbGU` |
| хэшируемая строка | `"fc/v1/dm\nc2VydmVyLWlkLWV4YW1wbGU\nmmg42klgyqzwneiskrelxms3j4\noln3om3moz4aai7yhwsmgvps5y"` |
| `chatId` | `lo2a5ewrojycetbvska5utmpxe` |

Личный чат создаётся первым событием: клиент вычисляет `chatId` и сразу делает `POST /v1/chats/<chatId>/events`. Сервер находит собеседника перебором участников (тот, для кого формула даёт этот `chatId`) и записывает `chats/<chatId>/meta.json`. Отдельного запроса «создать чат» нет. Чата с самим собой нет (404).

### `GET /v1/chats`

Чаты, где я участник, по `chatId`. Ответ 200:

```json
{
  "chats": [
    {
      "chatId": "lo2a5ewrojycetbvska5utmpxe",
      "kind": "dm",
      "members": ["mmg42klgyqzwneiskrelxms3j4", "oln3om3moz4aai7yhwsmgvps5y"],
      "epoch": 0,
      "createdAt": 1794787200000,
      "lastGseq": 17,
      "lastTime": 1794787260000
    }
  ]
}
```

`members` по возрастанию. `lastGseq` и `lastTime` относятся к последнему событию чата, которое ещё лежит на сервере; `null`, если таких нет (чат пуст после очистки по сроку, такой чат остаётся в списке).

### `POST /v1/chats/<chatId>/events`

Отправить событие. Заголовки:

| Заголовок | Значение |
|---|---|
| `Authorization` | `Bearer <токен>` |
| `Content-Type` | `application/octet-stream` (сервер не проверяет) |
| `Idempotency-Key` | `msgId` события, base32 16 байт, 26 символов; обязателен |
| `X-FC-Epoch` | эпоха события, десятичное u32; обязателен; у личного чата `0` |

Тело: зашифрованное событие, сырые байты, от 1 до 262144 байт. Сервер его не разбирает.

Ответ 200:

```json
{"gseq": 18, "time": 1794787261234, "duplicate": false}
```

- `gseq` и `time` выдаёт сервер; порядок и время в ленте берутся отсюда.
- Ответ приходит только после того, как событие записано на диск (`fsync`).
- Повтор с тем же `Idempotency-Key` от того же участника в тот же чат возвращает прежние `gseq` и `time` с `"duplicate": true` и ничего не записывает; тело повтора не сравнивается. Это действует и после перезапуска сервера, пока исходное событие не удалено по сроку. Клиент при обрыве связи повторяет отправку с тем же ключом.
- После записи сервер шлёт уведомления (раздел 6) и будит длинные запросы собеседника.

Ошибки:

| Статус | `error` | Причина |
|---|---|---|
| 400 | `bad_request` | неверный `chatId`, нет или неверный `Idempotency-Key` или `X-FC-Epoch`, пустое тело |
| 403 | `not_member` | чат существует, я не участник |
| 403 | `peer_removed` | собеседник исключён из семьи |
| 404 | `chat_not_found` | ни с одним участником `chatId` не сходится |
| 409 | `epoch_mismatch` | эпоха не равна текущей эпохе чата; в ответе `"epoch": <текущая>` |
| 409 | `idempotency_conflict` | этот `Idempotency-Key` уже использован мной в другом чате |
| 413 | `too_large` | тело больше 262144 байт; `"limit": 262144` |
| 507 | `storage_full` | мало места на диске |

### `GET /v1/events?after=<gseq>&limit=<n>&wait=<сек>`

Мои события (всех моих чатов) с `gseq > after`, от старых к новым. Это основной канал доставки.

- `after`: последний полученный `gseq`, по умолчанию 0.
- `wait`: если подходящих событий нет, сервер держит запрос до `wait` секунд (не больше 30) и отвечает сразу, как только появится событие для меня. Пока приложение открыто, клиент держит `wait=25` и сразу повторяет запрос после ответа.

Ответ 200:

```json
{
  "events": [
    {
      "gseq": 18,
      "time": 1794787261234,
      "chatId": "lo2a5ewrojycetbvska5utmpxe",
      "senderId": "mmg42klgyqzwneiskrelxms3j4",
      "devId": "aaaqeayeaudaocaj",
      "epoch": 0,
      "msgId": "aaaqeayeaudaocajbifqydiob4",
      "body": "<base64url тела события>"
    }
  ],
  "cursor": 18,
  "more": false,
  "oldestGseq": 1
}
```

- `cursor`: значение для следующего `after`. Клиент **всегда** заменяет свой курсор на `cursor`, даже если он меньше прежнего (сервер восстановили из старой копии). Если `more: false`, `cursor` равен последнему `gseq` на сервере, в том числе событий чужих чатов: номера сквозные, поэтому в `gseq` моих событий бывают пропуски, это нормально.
- `more: true`: событий больше, чем поместилось (`limit` или около 4 МиБ тел), клиент сразу запрашивает следующую страницу с `after=cursor`.
- `oldestGseq`: самый старый `gseq`, который ещё лежит на сервере (если журнал пуст, следующий номер). Если `after + 1 < oldestGseq`, часть событий после курсора могла быть удалена по сроку хранения: клиент показывает отметку «сообщения до <дата> с сервера уже удалены» и предлагает импорт архива. Для нового устройства с `after=0` это ожидаемо.
- `senderId` и `devId` поставил сервер по токену отправителя; `msgId` это его `Idempotency-Key`. Клиент всё равно проверяет подпись внутри тела.
- Пустой ответ (`events: []`) после ожидания это норма.
- При остановке сервера ждущие запросы получают пустой ответ 200.
- Запрос, который уже ждёт со старым токеном, дорабатывает до конца ожидания, даже если токен тем временем заменён (новый вход того же устройства через `auth/device`): проверка токена идёт в начале запроса. Следующий запрос со старым токеном получит 401. Исключение участника, наоборот, заканчивает его ждущие запросы сразу (403 `removed`).
- 403 `removed`, если участника исключили, в том числе во время ожидания.
- 400 `bad_request` при нечисловых `after`, `limit`, `wait`.

### `GET /v1/chats/<chatId>/events?before=<gseq>&limit=<n>`

История одного чата назад, для прокрутки. Возвращает до `limit` (по умолчанию 200, не больше 500) последних событий чата с `gseq < before` (без `before`: самые новые), в порядке от старых к новым.

Ответ 200:

```json
{"events": [ … как в /v1/events … ], "cursor": 5, "more": true, "oldestGseq": 1}
```

- `cursor`: `gseq` самого старого события в ответе; следующая страница: `before=cursor`. Если событий нет, `cursor` равен меньшему из `before` и следующего номера на сервере.
- `more: true`: на сервере есть ещё более старые события этого чата.
- Личный чат, который ещё не создан, но `chatId` которого сходится со мной и другим участником, отвечает пустым списком.

Ошибки: 400 `bad_request` (неверный `chatId` или параметры), 403 `not_member`, 404 `chat_not_found`.

## 6. Уведомления

### `PUT /v1/me/push`

Подписка Web Push для текущего устройства. Тело как `PushSubscription.toJSON()`:

```json
{"endpoint": "https://fcm.googleapis.com/fcm/send/…", "keys": {"p256dh": "<base64url 65 байт>", "auth": "<base64url 16 байт>"}}
```

`endpoint` только `https://` (до 2048 символов), `p256dh` несжатая точка P-256 (65 байт, первый 0x04), `auth` 16 байт; лишние поля (`expirationTime`) пропускаются. Новая подписка заменяет прежнюю. Ответ 204 без тела.

Ошибки: 400 `bad_request`, 409 `push_disabled` (на сервере `push = false`).

### `DELETE /v1/me/push`

Удалить подписку текущего устройства. Ответ 204, в том числе если подписки не было.

### Что приходит

На каждое новое событие (не на повтор) сервер шлёт уведомление на все устройства с подпиской **других** участников чата; устройствам отправителя, включая другие его устройства, уведомление не идёт. Исключённым участникам не идёт. Полезная нагрузка, зашифрованная по RFC 8291 (`aes128gcm`), это JSON

```json
{"chatId": "lo2a5ewrojycetbvska5utmpxe", "gseq": 18}
```

Текста и имён в уведомлении нет. Заголовки запроса к push-сервису: `TTL: 300`, `Urgency: high`. Service worker показывает «Новое сообщение» и имя чата из локальной базы. Подписку, на которую push-сервис ответил 404 или 410, сервер удаляет (`GET /v1/me` покажет `push: false`); клиенту стоит подписаться заново при следующем запуске.

## 7. Администрирование

Все запросы требуют токен администратора; иначе 403 `not_admin`.

### `POST /v1/admin/invites`

Тело пустое. Ответ 201:

```json
{"id": "<64 hex>", "code": "<26 символов base32>", "createdAt": 1794787200000, "expiresAt": 1795392000000}
```

`code` показывается только здесь, один раз: на сервере хранится лишь его SHA-256 (`id` это этот хэш в hex). Срок 7 суток.

### `GET /v1/admin/invites`

Ответ 200, по времени создания:

```json
{
  "invites": [
    {"id": "…", "createdAt": 1794787200000, "expiresAt": 1795392000000, "createdBy": "<userId>", "usedAt": null, "usedBy": null}
  ]
}
```

Использованные приглашения видны с `usedAt` и `usedBy` до конца срока. Просроченные удаляются ежечасной очисткой.

### `DELETE /v1/admin/invites/<id>`

Отозвать приглашение. 204; 404 `not_found`, если такого нет; 400 при неверном `id` (64 строчных hex-символа).

### `GET /v1/admin/users`

Ответ 200, по `userId`:

```json
{
  "users": [
    {
      "userId": "…",
      "name": "Мама",
      "admin": true,
      "removed": false,
      "removedAt": null,
      "devices": [{"devId": "…", "createdAt": 1794787200000, "push": true}]
    }
  ]
}
```

`name` взят из подписанного профиля (сервер его видит в открытом виде).

### `DELETE /v1/admin/users/<userId>`

Исключить участника. Ответ 204 (повтор тоже 204). Сразу после этого:

- все токены участника получают 403 `removed`, его ждущие `GET /v1/events` заканчиваются 403;
- `auth/device` для него отвечает 403;
- его события не принимаются, ему ничего не доставляется и не уведомляется;
- отправка в личный чат с ним отвечает 403 `peer_removed`;
- если он был администратором, перестаёт им быть.

Его прежние события остаются у собеседников и на сервере до конца срока хранения; в `GET /v1/users` он остаётся с `removed: true`.

Ошибки: 400 (неверный `userId`), 404 `unknown_user`, 409 `cannot_remove_self`.

### `GET /v1/admin/stats`

Ответ 200:

```json
{
  "version": "0.1.0",
  "dataBytes": 1234567,
  "freeBytes": 9876543210,
  "totalBytes": 32000000000,
  "events": 4210,
  "oldestGseq": 120,
  "lastGseq": 4329,
  "users": 5,
  "removedUsers": 0,
  "chats": 7,
  "retentionDays": 90,
  "push": true
}
```

`users`: число текущих участников, исключённые в него не входят (они считаются в `removedUsers`). `dataBytes`: сумма размеров файлов папки данных. `freeBytes`, `totalBytes`: место файловой системы, где лежит папка (доступное непривилегированному процессу); `null` там, где сервер не умеет это узнать (Windows). Когда свободного меньше `min_free_mb` из настроек (по умолчанию 100 МБ), отправка событий и вступление отвечают 507.

## 8. Срок хранения

- Сервер хранит события не дольше `retentionDays` (7-90, по умолчанию 90). Раз в час (и при запуске) удаляются целые дни журнала, вложения этих дней и просроченные приглашения.
- День удаляется, когда весь он (по UTC) старше срока относительно точки отсчёта: меньшее из «сейчас» и «время самого нового события плюс 7 дней». Поэтому часы сервера, убежавшие вперёд, не стирают всё, а отставшие только откладывают очистку.
- Удаляются только события; участники, профили и записи чатов остаются.
- Клиент узнаёт об удалённом по `oldestGseq` (раздел 5).

## 9. Что клиенту важно помнить

1. Курсор один на сервер: последний `cursor` из `GET /v1/events`. Хранить его надо после сохранения событий в локальной базе.
2. Одно и то же событие может прийти дважды (повтор после обрыва, история и лента). Клиент отбрасывает повторы по (`senderId`, `msgId`) или по `gseq`.
3. Отправка: событие в локальную очередь, затем `POST` с `Idempotency-Key = msgId`; при обрыве или 5xx повторять с тем же ключом. 409 `epoch_mismatch` в личном чате означает ошибку клиента (эпоха всегда 0).
4. 401 на любом запросе: войти заново через `auth/challenge` + `auth/device` с тем же `devId`, затем повторить запрос. 403 `removed`: показать экран «Вас отключили от семьи», запросы прекратить.
5. Ответы сервера не содержат имён и текста: имена берутся из подписанных профилей `GET /v1/users`, текст из расшифрованного тела.
6. Код администратора печатается в журнал сервера один раз, при создании папки данных.
